# Конфигурация

Образец: `.env.dist`. Файл `.env` в git не попадает.

## Общие

| Переменная | По умолчанию | Смысл |

## Обработка загруженных снимков

Запрос загрузки только проверяет файлы и кладёт их в хранилище (статус `queued`). Дату (штамп, EXIF, имя файла) и технику ставит фоновая очередь в процессе бэкенда. Когда кадры объекта кончаются, она ставит дату по соседям, проверяет серию камеры и один раз пересчитывает наблюдения и статусы. Прогресс — `GET /sites/{id}/photos/progress`, интерфейс показывает плашку «Обрабатываются снимки». После перезапуска оборванные кадры возвращаются в очередь.

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `UPLOAD__BACKGROUND` | `true` | `false` — прежняя обработка внутри запроса (тесты, отладка) |
| `UPLOAD__WORKERS` | `3` | Сколько кадров обрабатывать одновременно. Упор — в ML: на 8 ядрах около 30 кадров в минуту |
| `UPLOAD__TICK_S` | `5` | Как часто очередь смотрит новые кадры, если загрузка её не разбудила |

## Загрузка видео

Ручная загрузка отрывка с камеры (`POST /api/sites/{site_id}/cameras/{camera_id}/video`). Файл режется на кадры через ffmpeg, кадры идут в обычную фоновую очередь снимков. Нужен ffmpeg и ffprobe на сервере (в образе backend они есть).

| Переменная | По умолчанию | Смысл |

| `VIDEO__MAX_FRAMES` | `200` | Сколько кадров может получиться из одного отрывка. Больше — `422` с подсказкой, до какого шага увеличить |
| `VIDEO__DEFAULT_STEP_S` | `30` | Шаг кадров, если он не передан |
| `VIDEO__MIN_STEP_S` | `5` | Минимальный шаг |
| `VIDEO__MAX_STEP_S` | `3600` | Максимальный шаг |

## Снимки со стрима камер

Настройки читаются из окружения бэкенда, как остальные. Вложенные имена пишутся через `__`. Списки задаются JSON-строкой, например `STREAM__ALLOWED_NETWORKS=["192.168.1.0/24"]`.

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `STREAM__ENABLED` | `true` | Фоновый планировщик снимков; `false` выключает его. Ручной «Снять кадр сейчас» и пробный кадр от этого флага не зависят |
| `STREAM__HOURS` | `8-20` | Часы съёмки по поясу стройки. Конец не включается: `8-20` значит с 8:00 до 19:59 |
| `STREAM__TIMEZONE` | `Europe/Moscow` | Пояс IANA. По нему выбирается дата кадра |
| `STREAM__TIMEOUT_S` | `15` | Сколько ждать один кадр |
| `STREAM__CONCURRENCY` | `4` | Сколько ffmpeg-процессов одновременно. Лимит общий для планировщика и ручных снимков |
| `STREAM__TICK_S` | `15` | Как часто планировщик проверяет, каким камерам пора снимать |
| `STREAM__MAX_BACKOFF_S` | `3600` | Предел интервала после серии сбоев |
| `STREAM__BLOCKED_HOSTS` | `["postgres","minio","ml","backend","frontend","web"]` | Имена служб compose, на которые снимать нельзя |
| `STREAM__BLOCKED_NETWORKS` | пусто | Дополнительные закрытые сети (CIDR) |
| `STREAM__ALLOWED_NETWORKS` | пусто | Частные сети (CIDR), где стоят камеры стройки. По умолчанию закрыты все частные адреса |

Интервал съёмки задаётся на каждой камере (от 60 секунд до суток, по умолчанию 300). После трёх сбоев подряд интервал удваивается на каждый следующий сбой, но не дольше `STREAM__MAX_BACKOFF_S`. Удачный кадр возвращает интервал к обычному.

Адреса, которые сервис не снимает никогда: петля, link-local, «любой адрес», мультикаст, зарезервированные адреса и службы из `STREAM__BLOCKED_HOSTS`. Частные адреса закрыты, пока их не разрешит `STREAM__ALLOWED_NETWORKS`.

Для снимка нужен `ffmpeg`. Образ backend ставит его сам. При запуске без Docker он должен быть в `PATH`. Без него снимок отвечает `422 На сервере нет ffmpeg`.

### Прокси для телеграма

В России `api.telegram.org` заблокирован, поэтому бот ходит в Bot API через Xray.
Профиль compose `proxy`, поднимается `make dev-proxy` (локально) или `make up-proxy` (прод);
обычные `make dev` и `make up` его не включают.

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `XRAY__LINKS` | не задан | Одна или несколько ссылок `vless://`. Xray пингует все и шлёт трафик через живую с наименьшей задержкой. Разделитель — перевод строки или запятая, **не пробел**: пробел бывает в названии узла (`#Узел два`), и ссылка порвалась бы. Пусто — `xray-init` падает с понятной ошибкой, и Xray не запускается |
| `XRAY__HTTP_PORT` | `8080` | Порт HTTP-входа Xray внутри сети compose; наружу не публикуется |
| `XRAY__PROBE_URL` | `https://api.telegram.org/` | Что пингуется, чтобы считать ссылку живой. Именно телеграм: канал может работать «вообще», но быть заблокированным до Bot API |
| `XRAY__PROBE_INTERVAL` | `10s` | Как часто пинговать |
| `NOTIFY__TELEGRAM__PROXY_URL` | не задан | HTTP-прокси для Bot API. Профиль `proxy` подставляет его сам (`http://xray:8080`); вручную задают, только если прокси свой |

Из видов ссылок поддерживаются `security=none|tls|reality` и `type=tcp|ws|grpc|httpupgrade`.
Незнакомое сочетание — отказ с понятным текстом, а не outbound «на авось»: иначе канал
считался бы настроенным, а трафик бы не шёл.

`XRAY__LINKS` содержит учётные данные, поэтому приложению он не достаётся: в
`deploy/docker/common/core.yaml` переменная зануляется для сервиса `backend`, как уже
сделано с ключом LLM. Её читает только `xray-init`.

Проверить, что из ссылок собирается работоспособный конфиг, не поднимая весь стек:

```bash
make xray-check
```
