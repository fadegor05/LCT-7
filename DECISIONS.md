## D-001. Лицензия репозитория — ОТКРЫТО ⚠

**Статус:** не решено. Файла `LICENSE` в репозитории нет, значит формально
«все права защищены», а по ТЗ (разд. 7.2) код должен быть открытым.

**Развилка.** Всё семейство Ultralytics (YOLO26, YOLOE) — AGPL-3.0, и по позиции
разработчика это распространяется на обученные веса.
- **AGPL-3.0 для репозитория** — оставляет открытыми оба пути выбора детектора.
- **Apache-стек** (RF-DETR S/M, D-FINE, DEIM, MM-Grounding-DINO) — чище для
  внедрения у заказчика, но закрывает дорогу к Ultralytics.

**Рекомендация:** поставить AGPL-3.0 сейчас, выбор детектора отложить до G1.
Обратный порядок необратим: с Apache-репозиторием YOLOE уже не взять.

**Что сделает решение неверным:** если заказчик потребует закрытого внедрения
без покупки Enterprise-лицензии Ultralytics — тогда весь стек должен быть Apache
с самого начала.

## D-002. Окружение: venv + CUDA-сборка torch — ПРИНЯТО 2026-09-16

**Решение.** `.venv` в корне проекта, Python 3.12, запуск без активации через
`.venv\Scripts\python.exe`. Torch ставится **не с PyPI**, а с индекса PyTorch.
Зафиксировано: `torch==2.14.0+cu130`, `torchvision==0.29.0+cu130`,
`ultralytics==8.4.153`. Проверено на RTX 4060 Laptop (sm_89), драйвер 610.74.

**Почему.** Обычный `pip install torch` ставит сборку `+cpu`, и GPU молча не
используется. Порядок установки тоже важен: сначала `ultralytics`, потом torch —
иначе ultralytics подтягивает CPU-сборку как зависимость и перетирает CUDA-версию.

**Побочное.** На Windows пришлось выключить Smart App Control: он блокировал
неподписанные DLL из колёс pip (`WinError 4551` на `c10.dll`). Альтернатива без
изменения системы — работа в WSL2. Выключение SAC необратимо без переустановки
Windows — учтено и принято сознательно.

## D-003. Таксономия шире списка ТЗ — ПРИНЯТО 2026-09-16

**Решение.** Размечаем 24 класса вместо 8 из ТЗ: добавлены буровая установка,
башенный и гусеничный краны, копёр, установка «стена в грунте», автобетононасос,
экскаватор-погрузчик, асфальтоукладчик и другие. Иерархия coarse → fine, при
неуверенности ставится coarse-класс.

**Почему.** На выданных снимках чаще всего встречаются именно буровые установки и
башенные краны, которых в списке ТЗ нет, и именно они дают однозначный сигнал
этапа работ (`research/part_I`, вывод 5). ТЗ (разд. 6.2) расширение прямо
разрешает.

**Что сделает решение неверным:** если на сверке по §6 `LABELING_SPEC.md`
окажется, что размечающие не различают пару классов стабильно — эта пара
схлопывается в coarse.

## D-004. Валидация по двум доменам, сплит по площадкам и камерам — ПРИНЯТО

**Решение.**
- Фото организаторов: grouped K-fold **по площадкам**, hold-out — новые снимки
  других объектов из открытых источников.
- Kaggle CCTV: **leave-camera-out** по прореженным кадрам, 2–3 камеры целиком в
  hold-out.
- В отчёте всегда матрица «обучение на домене X → тест на домене Y» и срезы по
  сезону, ракурсу, размеру объекта.

**Почему.** Снимки идут сериями одной площадки, в одну дату их бывает несколько.
Случайный сплит по кадрам даст утечку и завышенную оценку. У Kaggle то же самое
по камерам: родной `train`/`valid` до проверки пересечения камер использовать
нельзя.

## D-005. Данные на A100 возим через HuggingFace — ПРИНЯТО

**Решение.** Приватный dataset-репозиторий на HF; на сервере задача тянет данные
напрямую. `culab push` используется только для кода.

**Почему.** У `jupyter.culab.ru` эфемерный диск (данные пропадают при
перезагрузке пода), а фильтр `culab push` исключает `*.csv`, архивы и веса.
Побочная выгода: у HF есть ревизии, и в документации можно сослаться на точную
версию данных — это работает на критерий воспроизводимости.

**Ограничение.** Снимки организаторов и всё производное — только в приватном
репозитории.

## D-006. Укрупнение этапов — по наблюдаемости, не по структуре справочника — ПРИНЯТО 2026-09-17

**Решение.** Работы справочника сводятся в **8 наблюдаемых этапов** плюс один
блок «вне наблюдения». Критерий слияния ровно один: две работы идут в один этап,
если камера не может их различить. Сопоставление живёт отдельной таблицей
«код работы → наблюдаемый этап» (многие-к-одному), версионируется рядом с
`ruleset`, справочник и парсер не трогаются.

| Наблюдаемый этап | Коды | Маркеры техники |
|---|---|---|
| Подготовка площадки | `10.*` | бульдозер, экскаватор, самосвал, автокран |
| Котлован и земляные работы | `12.3.1`, `12.3.3`, `12.3.7` | экскаватор, самосвал |
| Сваи и ограждение котлована | `12.3.2`, `12.3.5`, `12.3.6` | буровая установка, гусеничный кран |
| Фундамент и подземная часть | `12.3.4`, `12.3.9`–`12.3.11` | автобетононасос, бетоносмеситель |
| Каркас надземной части | `12.4.4`, `12.4.5`, `12.4.8`–`12.4.10`, `12.4.28`–`12.4.30` | башенный кран, бетононасос |
| Кровля и фасад | `12.4.11`, `12.4.31`, `12.4.32`, `12.4.37`–`12.4.57`, `12.6.1` | автовышка, подъёмник, автокран |
| Наружные сети | `12.5.1` | экскаватор, трубоукладчик |
| Благоустройство | `12.7.*`, `12.4.12`, `12.4.14` | каток, асфальтоукладчик, самосвал |
| **Вне наблюдения** | `12.5.2`, `12.6.2`–`12.6.13`, `12.4.33`–`12.4.36` | маркеров нет |

Дорожно-тоннельная ветка (`12.1`, `12.2`, `12.3.8`, `12.4.13`–`12.4.27`) —
отдельный профиль под тип объекта «Дороги», в демо не берётся.

**Почему.** Укрупнять разрешено прямо (`QA_SESSION` 17:28), как и ограничиться
внешней аналитикой (32:19); ментор советовал качественно по ограниченному числу
разделов, а не широко и поверхностно (34:11). Различие, которого не видно на
кадре, не даёт пользы, но порождает ложные отклонения.

**Расхождение, требующее уточнения.** В Q&A звучит «работы сгруппированы по 4
этапам» и «4 уровня детализации», а в выданном файле — 2 раздела верхнего уровня
(10 и 12), 21 подраздел и **5 уровней** вложенности. Цифра «4» ни на что в файле
буквально не ложится. Вопрос задать в чате задачи.

**Что сделает решение неверным:** если на вход подадут график, детализированный
до уровня, где наши укрупнённые этапы перестают быть подмножествами его строк.
Защита — сопоставление таблицей, а не переписыванием справочника.

## D-007. Ненаблюдаемые работы дают предупреждение, а не вердикт — ПРИНЯТО 2026-09-17

**Решение.** Для блока «вне наблюдения» (внутренняя отделка, двери, электрика,
внутренние сети) система не выносит суждения о соответствии графику, а выдаёт
явное «работы вне зоны контроля ИИ, требуется дополнительная проверка».
То же поведение — когда часть площадки не попала в кадр.

**Почему.** Ровно об этом просили на 13:01: не анализировать молча, а выводить
предупреждение. Плюс в контракте правил уже заложено `checkable_by_equipment:
false`. Ограничение превращается в заявленную заказчиком функцию, а не в дыру.

**Что сделает решение неверным:** ничего в пределах этого хакатона. Риск
обратный — соблазн тихо пропустить эти работы и получить вопрос жюри «а почему
по отделке всегда всё хорошо».

## D-008. Кластеризация площадок по пикселям — ЗАКРЫТО 2026-09-17

**Решение.** `site_id` проставляется вручную в манифесте; в интерфейсе —
привязка пачкой. Автоматическое восстановление площадки из изображения не
делаем.

**Почему.** E7: на 862 парах SIFT + RANSAC не разделяет `same_date`, `same_site`
и `diff_site` — медиана 4 инлаера везде. Контроль пайплайна пройден (кадр сам с
собой 900/900). У снимков нет визуального перекрытия даже внутри одного выезда.
Способ привязки отдан команде явно (08:50), и простое решение здесь надёжнее.

**Важно для позиционирования:** это свойство выданной подборки, а не задачи. В
эксплуатации камера стационарна, `camera_id` даёт группировку бесплатно.
