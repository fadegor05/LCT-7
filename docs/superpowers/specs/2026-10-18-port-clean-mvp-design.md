# Перенос функционала `clean-mvp` поверх `main`

## Обзор

`clean-mvp` — переписанный с нуля проект (нет общего предка с `main`). Его нельзя
смерджить, и cherry-pick коммитов не применим. `main` — основа и работает в проде.
Цель: функции, которых нет в `main`, появляются в нём как обычные фичи поверх
существующей структуры.

## Правила (приоритет сверху вниз)

1. `main` главнее. Существующее поведение, API, имена таблиц и бизнес-логика не меняются.
   Вход/регистрация, лимит запросов, правила этапов — как в `main`.
2. Структура `main` остаётся (`domains/photo`, `domains/utility`, `assessment`,
   `observation`...). Переименований доменов нет. Новый функционал кладётся в новые
   модули или расширяет существующие.
3. Миграции — новой цепочкой поверх `0011_user_auth`, номера `0012+`. Миграции
   `clean-mvp` не копируются, а переписываются под схему `main`. Только аддитивные
   изменения (новые таблицы/колонки с default или nullable), без удалений.
4. API `main` обратно совместим: новые поля необязательные, новые эндпоинты — под
   новыми путями.
5. Источник логики и тестов — `git show clean-mvp:<путь>`. Код адаптируется под
   соглашения `main`, а не копируется поверх.
6. Каждая единица (U-n) завершается зелёными `make test`, `make front-check`, `make ml-test`
   (по затронутым частям) и отдельным коммитом.

## Единицы переноса (в порядке зависимостей)

Для каждой первый шаг — gap-анализ: что из `clean-mvp` уже есть в `main` (тогда
пропускаем) и что нет (переносим). Источник — план в
`git show clean-mvp:docs/superpowers/plans/<файл>`.

| U | Единица | Источник (план `clean-mvp`) | Заметки |
|---|---|---|---|
| U1 | Камеры: модель, рабочая зона-полигон, API, список камер и окно камеры во фронте | 03-2, 05-2, 05-6 | в `main` камеры как понятия нет; привязка существующих кадров (`photo`) к камере необязательная |
| U2 | Снимки со стрима: ffmpeg-адаптер, планировщик в рабочие часы объекта (8:00–20:00), «Снять кадр сейчас», статус стрима | 05-10, spec stream-capture | зависит от U1; кадры идут через существующий конвейер `photo` |
| U3 | Зона на кадрах: `in_zone` у рамки, контур зоны, «Вне зоны» | 05-7 | в `main` `in_zone` частично есть, сверить |
| U4 | Миниатюры кадров с рамками, подписи рамок по-русски (шрифт с кириллицей) | 05-5, 05-8 | `thumb` есть в `main` в одном месте, сверить |
| U5 | Отчёт A4 по объекту и «Скачать отчёт PDF» | 05-7 | в `main` нет |
| U6 | Методика карточками, «Объединить этапы», «Веха», шаг 1 на полном файле графика, повтор обработки кадров | 05-5, 05-6, 05-7 | не ломать `schedule`/`methodology` из `main` |
| U7 | Этап по комплекту, «Неполный комплект», «Отставание от графика» | 05-8 | в `main` есть похожее (stage-kit), переносить только отсутствующее |
| U8 | Штамп даты: профили 2592×1944 и 1920×1080, эталоны, `eval.py` | 04 | в `main` есть чтение штампа, сверить; тяжёлые данные `ml/data` не трогать |
| U9 | Ассистент: отличия | 03-4 | в `main` ассистент есть, брать только недостающее |
| U10 | Документация (`documentation/`) под новый функционал | 06 | в конце |

Вне объёма: вход/регистрация (остаются из `main`), перенос структуры доменов,
удаление чего-либо из `main`, `ml/data`, `deploy/*` кроме того, что нужно новой фиче
(например, ffmpeg в образе).

## Процесс DEV

Одна единица — одна задача субагента (Haiku, TDD). Сначала gap-анализ и короткий
отчёт, затем реализация. Я проверяю независимо: тесты, дифф, что тесты `main` не
изменены и проходят. Субагенту — одна консолидированная правка, затем я правлю сам.

## Тестирование

Бэкенд — pytest на PostgreSQL (testcontainers, нужен Docker). Фронт — Vitest + MSW.
Регрессия: набор тестов `main` должен остаться зелёным без правок существующих тестов.

## Критерии готовности

- [ ] Ветка `port/clean-mvp-features` от `main`, PR в `main`.
- [ ] Каждая единица U1–U10 перенесена или обоснованно пропущена (уже есть в `main`).
- [ ] Миграции `0012+` применяются на БД `main` и откатываются.
- [ ] Все тесты `main` зелёные без изменения существующих тестов.
- [ ] Вход/регистрация и прежние эндпоинты работают как раньше.
