# Система уведомлений

Дата: 2026-10-18
Ветка: `feat/notifications`

## Цель

У пользователя появляется личная лента уведомлений: запись в БД, шторка на сайте
и — по его выбору — дублирование в телеграм.

Итерация инфраструктурная. Источники событий (отклонения, сбои камер, готовность
отчётов) в неё не входят: домены подключатся к готовому шву позже. Чтобы проверить
систему без источников, предусмотрен служебный эндпоинт создания тестового
уведомления.

### Критерий успеха

Нажал кнопку «тестовое уведомление» → в шторке появилось новое с бейджем в шапке,
в привязанный телеграм пришло сообщение. Открыл шторку → бейдж погас, пометки
«новое» видны до закрытия шторки.

## Решения и их границы

- **Тип уведомления — не постгресовый `ENUM`.** Питоновский `StrEnum` плюс колонка
  `String(64)`, как уже сделано в `assessment/models.py`. Новый тип не требует
  миграции.
- **Каналы — через адаптеры.** В этой итерации реально работает только телеграм.
  Интерфейс рассчитан на почту и СМС, но их файлов пока нет.
- **Телеграм получает апдейты long polling'ом** в фоновой задаче. Webhook требует
  публичного HTTPS, которого нет на localhost.
- **Настройки доставки — только привязка канала**, без фильтров по типам и
  важности.
- **Отправка при создании, без outbox.** Осознанный компромисс, см. «Принятые
  риски».

## Модель данных

Новый домен `backend/app/domains/notification/` — плоская директория по конвенции
проекта: `models.py`, `schemas.py`, `repository.py`, `service.py`, `router.py`,
`provider.py`.

### `notifications`

| Поле | Тип | Смысл |
|---|---|---|
| `id` | `Uuid` PK, default `uuid4` | |
| `user_id` | `Uuid` FK `app_user.id` ON DELETE CASCADE | индекс |
| `type` | `String(64)` | `NotificationType(StrEnum)` в питоне, строка в БД |
| `title` | `String(255)` | заголовок в шторке |
| `body` | `Text` | текст сообщения |
| `link` | `String(500)` nullable | относительный путь фронта, куда ведёт клик |
| `read_at` | `DateTime(tz)` nullable | `NULL` — непрочитанное |
| `created_at` | `DateTime(tz)` server_default `now()` | |

Индекс `(user_id, created_at DESC)`: шторка всегда читает ленту одного пользователя
в обратном хронологическом порядке.

Стартовый состав `NotificationType`: `system` (служебные и тестовые). Остальные
значения добавят домены-источники, когда подключатся.

### `user_channels`

| Поле | Тип | Смысл |
|---|---|---|
| `id` | `Uuid` PK, default `uuid4` | |
| `user_id` | `Uuid` FK `app_user.id` ON DELETE CASCADE | |
| `channel` | `String(32)` | `ChannelKind(StrEnum)`: `telegram` |
| `address` | `String(255)` | для телеграма — `chat_id` строкой |
| `enabled` | `bool`, default `true` | тумблер «слать сюда», отдельно от факта привязки |
| `linked_at` | `DateTime(tz)` | |

`UniqueConstraint(user_id, channel)` — один адрес на канал на пользователя.

### `channel_link_tokens`

| Поле | Тип |
|---|---|
| `token` | `String(32)` PK |
| `user_id` | `Uuid` FK `app_user.id` ON DELETE CASCADE |
| `channel` | `String(32)` |
| `expires_at` | `DateTime(tz)` |
| `used_at` | `DateTime(tz)` nullable |

TTL токена — 15 минут. Хранится в БД, а не в памяти процесса: в деве бэкенд поднят
с `--reload`, и правка любого файла убила бы токены посреди привязки.

Все три модели импортируются в `app/models.py`, иначе Alembic их не увидит.
Миграция — одна, следующая после `0012`.

## API

Все роуты под `require_auth`, монтируются в `app/plugins/routing.py`.

| Метод | Путь | Поведение |
|---|---|---|
| `GET` | `/notifications` | лента текущего пользователя, `limit`/`offset`, плюс `unread_count` |
| `POST` | `/notifications/read` | `UPDATE ... SET read_at = now() WHERE user_id = :me AND read_at IS NULL`; возвращает число помеченных |
| `GET` | `/users/me/channels` | привязки: канал, замаскированный адрес, `enabled` |
| `POST` | `/users/me/channels/{channel}/link` | выдать токен; для телеграма вернуть `t.me/<bot>?start=<token>` |
| `PATCH` | `/users/me/channels/{channel}` | `{enabled: bool}` |
| `DELETE` | `/users/me/channels/{channel}` | отвязать: удалить строку, историю уведомлений не трогать |
| `POST` | `/notifications/test` | создать тестовое уведомление себе |

Если канал не настроен на сервере (нет токена бота), `link` отвечает ошибкой
«канал не настроен», а не выдаёт нерабочую ссылку.

### Шов для источников событий

```python
await notification_service.notify(
    user_id=...,       # адресат ровно один, рассылок на группу нет
    type=...,          # NotificationType
    title=...,
    body=...,
    link=...,          # необязательно
)
```

Домены `assessment` и `camera` позже зовут только этот метод и ничего не знают ни
про каналы, ни про телеграм.

## Адаптеры каналов

`app/adapters/notify/`, по образцу `adapters/storage`.

```python
# base.py
class ChannelMessage(BaseModel):
    title: str
    body: str
    link: str | None          # абсолютный URL; адаптер решает, как его подать

class NotifyError(Exception): ...

class NotificationChannel(Protocol):
    kind: ClassVar[ChannelKind]
    async def send(self, address: str, message: ChannelMessage) -> None: ...
```

- `log.py` — `LogChannel`, пишет в логгер. Умолчание и то, что используют тесты.
- `telegram.py` — настоящий канал.
- `factory.py` — собирает `ChannelRegistry` (`dict[ChannelKind, NotificationChannel]`)
  в `Scope.APP`. Телеграм попадает в реестр только при заданном токене, иначе на
  его месте `LogChannel`.

Добавить канал = один файл плюс строка в фабрике.

## Телеграм

Три части:

1. **`TelegramClient`** — обёртка над httpx: `send_message(chat_id, text)` и
   `get_updates(offset, timeout)`. Единственное место, знающее про Bot API.
2. **`TelegramChannel`** — реализует `NotificationChannel`, форматирует
   `ChannelMessage`, зовёт клиент.
3. **`TelegramLinkPoller`** — фоновая задача по образцу `StreamCapture`:
   `start()`/`stop()`, запуск из `lifespan` через `start_telegram_poller(container,
   settings)` рядом с `start_stream_capture`, только при заданном токене.

Цикл поллера: `getUpdates` с таймаутом 25 с. Увидел `/start <token>` — находит
токен, проверяет срок и что не использован, создаёт или обновляет `user_channels`
с `address = chat_id`, гасит токен, отвечает в чат «Готово, уведомления
привязаны». Просроченный или погашенный токен — ответ «ссылка устарела».

`offset` хранится в памяти задачи. Телеграм держит апдейты сутки, после рестарта
поллер их перечитает; повторный `/start` по погашенному токену безвреден. Таблица
под курсор не нужна.

## Доставка

`NotificationService.notify()` пишет строку и **после коммита** запускает
`asyncio.create_task`.

Задача не может пользоваться сессией запроса — к моменту её выполнения запрос
закрыт. Она берёт свою сессию из `async_sessionmaker`, грузит `user_channels` с
`enabled = true`, шлёт через реестр. Ошибка канала пишется в лог и не влияет на
HTTP-ответ.

## Настройки

```
NOTIFY__TELEGRAM__TOKEN          # нет токена — канал деградирует в LogChannel
NOTIFY__TELEGRAM__BOT_USERNAME   # для ссылки t.me/<bot>?start=<token>
NOTIFY__PUBLIC_URL               # база для абсолютных ссылок в сообщениях
```

Добавляются в `.env.dist` закомментированными, с пояснением про деградацию.
Токен не попадает в логи, `chat_id` в ответах API маскируется.

## Фронтенд

### Примитив

Новый `components/ui/Drawer.tsx` — панель справа на всю высоту. Логика закрытия
(Escape, возврат фокуса на прежний элемент) выносится из `Dialog` в хук
`components/ui/useDismissable.ts`; `Dialog` переходит на него без изменения своего
публичного API. Это единственная правка существующего кода.

### Слой API

`api/notifications.ts` — функции и хуки TanStack Query. Zod-схемы
(`notificationSchema`, `userChannelSchema`) в `api/schemas.ts`. Ключи в `keys.ts`:

```ts
notifications: ['notifications'] as const,
channels: ['me', 'channels'] as const,
```

Бейдж опрашивает `keys.notifications` с `refetchInterval: 30_000`. Вебсокетов в
проекте нет, полминуты для стройки достаточно.

### Компоненты

`features/notifications/`:

- `NotificationBell.tsx` — иконка в `AppLayout` с бейджем `unread_count`, скрыт при
  нуле;
- `NotificationDrawer.tsx` — лента, пустое состояние, клик по элементу ведёт по
  `link` и закрывает шторку;
- `NotificationItem.tsx` — иконка по `type`, заголовок, текст, относительное время.

### Поведение шторки

При открытии сразу уходит `POST /notifications/read`, бейдж в шапке гаснет. Список
при этом рисуется по снимку множества непрочитанных, снятому в момент открытия,
поэтому пометки «новое» видны, пока шторка открыта. Закрыл и открыл снова — лента
чистая.

### Личный кабинет

Новая страница `pages/ProfilePage.tsx`, маршрут `/profile` внутри `RequireAuth`.
Имя пользователя в шапке `AppLayout` становится ссылкой на неё.

Содержимое: ФИО с сохранением через существующий `PATCH /users/me`, ниже
`features/profile/ChannelList.tsx` — карточка на канал с «Привязать» (открывает
`t.me/...` в новой вкладке и начинает опрашивать `keys.channels`, чтобы поймать
момент привязки), «Отвязать» и тумблером «Слать сюда».

### Моки

Обработчики MSW над `db.ts` для всех семи эндпоинтов, включая правдоподобную
привязку телеграма без настоящего бота. Те же обработчики идут в тесты.

## Тестирование

Бэкенд:

- `LogChannel` и подменный `TelegramClient` (стаб, httpx не трогаем) покрывают
  доставку и разбор `/start`;
- жизненный цикл токена привязки: выдача, погашение, просрочка, повторное
  использование;
- `POST /notifications/read` помечает только свои непрочитанные;
- живой токен бота для тестов не нужен.

Фронтенд:

- `Drawer` и каждый новый компонент — свой `*.test.tsx`;
- страница профиля через `renderRoute('/profile')`;
- главный сценарий: открыл шторку → ушёл `POST /notifications/read` → бейдж исчез,
  пометки «новое» остались до закрытия;
- пороги покрытия в `vite.config.ts` должны остаться зелёными.

## Принятые риски

**Отправка без outbox.** Выбран вариант с `asyncio.create_task` после коммита
вместо таблицы доставок с фоновым воркером. Следствия:

1. Если транзакция запроса откатится уже после того, как задача успела отправить
   сообщение, в телеграм уйдёт уведомление о событии, которого не было.
2. Сбой сети или Bot API теряет сообщение: ретраев нет, статуса доставки в БД нет.

Для инфраструктурной итерации без реальных источников событий это приемлемо.
Когда к `notify()` подключатся отклонения, к вопросу стоит вернуться: outbox
(`notification_deliveries` + воркер с `FOR UPDATE SKIP LOCKED`, как в
`StreamCapture`) закрывает оба случая.

## Что в объём не входит

- Источники событий — отклонения, сбои камер, готовность отчётов.
- Каналы «почта» и «СМС»: интерфейс рассчитан на них, реализаций нет.
- Фильтры доставки по типу уведомления или важности.
- Групповые рассылки: у уведомления ровно один адресат.
- Вебсокеты и server-sent events: бейдж обновляется опросом.
