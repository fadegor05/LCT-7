# Поведение clean-mvp в main: серия фиксов

## Зачем

На стенде main (snmpsh.ru, `sha-b466e26`) при подготовке демо всплывает:

- ни у одного из 301 кадра нет камеры: при загрузке камеру не выбрать;
- дата ни у одного кадра не со штампа, только из имени файла или вручную; имя файла у
  выгрузок с камер — момент выгрузки, а не съёмки (49 кадров Березников «за 27.09»);
- камера со стримом ни разу не попробовала снять кадр (`STREAM__ENABLED=false`);
- итог «Отклонений нет» рядом с четырьмя критичными отклонениями (Березники);
- три критичных отклонения из одного снимка за день, под которым сам стенд пишет
  «по одному кадру вывод делать нельзя» (Москва, Пермь);
- этап одновременно «опережает на 57 дней» и с критичным отклонением.

В clean-mvp это решено. Переносим поведение, а не код целиком.

## Правила

1. Структура main остаётся: домены `photo`, `utility`, `schedule`, `methodology`, имена
   таблиц и пути API. Новое — новыми модулями или расширением существующих.
2. Миграции — продолжение цепочки main (`0013+`), только аддитивные.
3. API обратно совместим: новые поля необязательные, новые эндпоинты — новыми путями.
   Ветки `feat/notifications` и прочие от main должны ребейзиться без переписывания.
4. Логика и тесты берутся из clean-mvp (`../LCT-7-clean`, ветка `feat/clean-project`) и
   адаптируются под соглашения main.
5. Тесты main, проверяющие старое ошибочное поведение, правятся вместе с поведением —
   с пояснением в описании PR.
6. Каждый PR зелёный: `make check`, тесты бэкенда, `make front-check`.

## Ветки

Интеграционная ветка `port/clean` от `main`. Каждый пункт ниже — ветка
`port/clean-<n>-<тема>` и PR в `port/clean`. В `main` — один PR в конце, после прогона
демо-сценария на стенде.

## PR

| № | Тема | Что меняется в поведении | Источник в clean |
|---|---|---|---|
| 1 | Приём кадров | Выбор камеры при загрузке (обязателен, если камеры есть); время со штампа камеры по умолчанию; имя файла выгрузки — не время съёмки; обработка в фоне, а не в запросе загрузки, с прогрессом | `domains/frame/{upload,processing,timing}.py`, `features/observations` |
| 2 | Движок вывода | Пакет `assessment/engine` из `app/engine` clean за адаптером к входам/выходам main; итог объекта по худшему этапу и согласован с отклонениями; день с одним кадром не порождает критичных; «опережает» и критичное не сосуществуют | `app/engine/*`, `domains/assessment/{recompute,views,trigger}.py` |
| 3 | Наблюдения | Сводка дня по всем камерам, группировка кадров по камерам, «Все дни» при малом числе кадров, кадр крупно с рамками | `domains/observation/{daily,activity,series}.py`, `pages/ObservationsPage` |

Порядок: 1 → 2 → 3 → 4, затем 5–7 в любом порядке, 8 последним.

## Проверка в конце

На стенде с базой main после миграций перезаливаются демо-объекты скриптами из PR 8,
и проходится сценарий `docs/demo.md`. Каждый пункт из «Зачем» проверяется руками.
