# Разбор макета MVP: сходство с кейсом, Q&A и контрактом

Ревью макета [«ЛЦТ — MVP: экраны»](https://claude.ai/artifact/RkxaZyETKzAYocADqQpRCd)
(design-канвас, 10 артбордов, версия `1789987760-733b`, дизайн-система `lct7`)
против трёх источников требований:

| Источник | Что это | Где лежит |
|---|---|---|
| **ТЗ кейса** | «Автоматизированный сервис поиска нарушений на строительных площадках Москвы», ЛЦТ-2026, задача №7 (ДГП) | `lct/7. Департамент градостроительной политики города Москвы.pdf` |
| **Q&A-сессия** | запись 46 мин с постановщиком, конспект с таймкодами | `ml/docs/QA_SESSION.md` |
| **Контракт** | форматы обмена между зрением, методикой и интерфейсом | `ml/docs/CONTRACTS.md` |

Состояние кода на момент ревью: ветка `ML` на `158c395` (21.09), рабочая модель
`weights/mocs_mix_best.pt` — mAP50 **0.426**, точность 0.67, полнота 0.56,
совпадение статусов этапов **8/10** (на невиданных площадках честно **5/7**),
порог 0.25 (`ml/EXPERIMENTS.md`, E14). Бэкенд: домен не реализован — в
`backend/app/modules` только `user` и `utility`. Фронтенд: `App.tsx` и `main.tsx`.
То есть макет сейчас опережает код целиком.

## 1. Карта фреймов

| № | Фрейм | Роль в сценарии |
|---|---|---|
| 1 | Стройки | список объектов + сквозной список отклонений по всем стройкам |
| 2 | Новая стройка: график и крупные этапы | импорт КСГ, укрупнение работ в этапы, валидация файла |
| 3 | Методика (шаг 2) | правила «этап → техника» в мастере создания |
| 3а | Методика объекта (вкладка) | те же правила как вкладка объекта |
| 4 | Камеры | список камер, стрим и рабочая зона |
| 4а | Камеры: настройка камеры и зоны | то же с открытым диалогом (отличие от 4 — одна строка состояния `pop: 'edit'`) |
| 5 | Обзор | итог по объекту, таблица этапов, список отклонений, последнее наблюдение |
| 6 | Наблюдения | техника по дням и камерам, ленты кадров, кадры без даты, загрузка |
| 7 | Отклонение: критичное | карточка отклонения «нет нужной техники» |
| 7а | Отклонение: гипотеза | карточка гипотезы «простой техники» + решение инженера |

Основной UC («завести стройку → загрузить кадры → прочитать статус → разобраться
в отклонении») закрыт фреймами 2 → 3 → 6 → 5 → 7/7а. Дыр в маршруте нет.

### 2.3 Критерии оценки (ТЗ, разд. 8) — что макет закрывает

- **8.1 «механизм объяснения предупреждений»** — закрыт лучше всего: правило +
  источник + уверенность + наблюдаемость + «чего это не доказывает».
- **8.3 «явная и проверяемая связь»** — от статуса до правила ровно два перехода
  (5 → 7 → «Сработавшее правило» / «Методика этапа»).
- **8.3 «интерфейс и юзабилити: быстрая оценка статуса»** — итог на фрейме 5
  читается за секунды.
- **8.2 «скорость работы»** — **нигде не показана**, хотя это отдельный критерий.

## 4. Соответствие контракту (`ml/docs/CONTRACTS.md`)

### 4.1 Где макет и контракт совпадают дословно

Дизайн-система макета (`ds/lct7/components/bundle.js`) содержит ровно те же
словари, что и контракт, — это лучшее, что есть в этом макете с точки зрения
интеграции:

| Контракт | Компонент макета | Значения |
|---|---|---|
| `status` (6 значений) | `StatusBadge` | `ahead / ontrack / behind / notstarted / unobserved / unverifiable` — **все шесть** |
| `confidence` — ординальный, не число | `ConfidenceMeter` | `high / medium / low`, три сегмента, без процентов |
| `date_source` | `DateSource` | `channel / exif / stamp / neighbors / manual` — совпадает с v2-дополнением контракта, §«Снимок: источник даты» |
| Алерт: `expected`, `observed`, `evidence`, `rules_fired`, `confidence`, `observability`, `cannot_claim` | фрейм 7 | все семь полей на экране |
| Количество техники = **максимум по кадрам**, не сумма | 6: «не менее 2», сноска про ракурсы | совпадает |
| `not_started` ≠ `not_observed` | 1: «Недостаточно данных», «Данные устарели · 35 дн.» | различие введено на уровне объекта |

### 4.2 Чего в контракте нет, а в макете появилось

Это не ошибки макета — это места, где **контракт надо дописать**, иначе бэкенд
и фронт разъедутся:

| Понятие макета | Где | Что добавить в контракт |
|---|---|---|
| **Важность** отклонения (`Критично` / `Внимание`) с потолком для гипотез | 1, 5, 7, 7а | поле `severity`; формула на фрейме 7 в `details` уже написана: тип + дни + уверенность + наблюдаемость, потолок опускает низкая уверенность или наблюдаемость |
| **Маркерная техника** этапа | 3, 5 («Факт по маркеру») | флаг `marker` у машины в правиле; сейчас в контракте есть только `obligation: normative/logical` и `required/auxiliary` |
| **«Обычно N»** — справочное количество | 3 | поле `typical`, явно не влияющее на дни отставания |
| **Камера** как сущность с рабочей зоной | 4, 4а, 6, 7а | `camera_id`, полигон зоны; в контракте камеры нет вообще |
| **Решение инженера** по гипотезе | 7а | поле решения + ключ, по которому оно переживает пересчёт методики |
| **Возможная причина** — связь отклонения с отклонением | 7 | ссылка `caused_by` на другое отклонение |

### 4.3 Где макет расходится с контрактом по смыслу

1. **Статус «Не начата» на фрейме 5 нарисован обычным текстом**, а не бейджем, —
   три строки таблицы из шести. В дизайн-системе бейдж `notstarted` есть.
2. **Бейдж `unobserved` («Не наблюдалось») не использован ни разу.** При этом
   различать «не начат» и «не наблюдалось» — требование контракта и пункт 5
   Definition of Done в `docs/product.md`. На макете это различие **нечем
   показать жюри**.
3. **Будущие этапы помечены «Не начата»** (Бетонирование плиты 23.09–05.10 при
   данных на 18.09). По контракту `not_started` — это «плановое начало прошло,
   техника не наблюдается», то есть утверждение о стройке. Для этапа, который
   ещё не должен был начаться, нужен отдельный нейтральный вид («по плану ещё не
   начат»), иначе таблица пугает там, где всё в порядке.

## 5. Расхождения, которые надо решить (по убыванию цены)

### 5.1 Видео и стрим на фрейме 6

Q&A 07:37: обработка видео и потоковых данных **не предусмотрена**;
`docs/product.md` §11 повторяет это как явную границу MVP. На фрейме 6 три
вкладки загрузки — фото, видео с нарезкой, RTSP-стрим с периодичностью, плюс
«короткие клипы-доказательства».

Цена: RTSP в демо — это живой сервис, который падает на защите; видео — ещё
один тракт хранения и нарезки. Оба не дают ни одного балла по критериям 8.1–8.4,
потому что оцениваются снимки.

Предложение: оставить **фото** и **нарезку видеофайла на кадры** (дёшево,
ffmpeg, и честно формулируется как «мы принимаем видео, но анализируем кадры»),
**убрать живой стрим** или показать его как заглушку «на будущее». Про клипы не
заявлять.

### 5.2 Язык объяснения активности на фрейме 6

Макет объясняет активность так: «Движение: изображение внутри рамки изменилось
между 10:10 и 12:50». D-007 в редакции от 20.09 движение как признак **снял** и
поднял в опорные **парную технику** (74% времени простоя экскаватора — это
«рядом нет ни одного самосвала»); зона оставлена вспомогательной; Q&A 21:53
показывает, что заказчик сам сводит задачу к зоне, а не к движению.

То есть экран объясняет вывод признаком, которого в методике больше нет. Правка
текстовая и бесплатная: основания читать как «Парная техника: самосвал под
погрузкой — есть/нет», «Зона: внутри/вне рабочей зоны камеры», «Рабочий орган:
ковш в грунте» — и `Неизвестно` для кранов как нормальный ответ (по разметке
человек не выносит суждение о кранах в 61 случае из 62).

### 5.3 Второго сигнала — признака сцены — в макете нет

G1-03 закрыт решением «признаки сцены нужны» (E5: одно наблюдение подтверждает
2.1 этапа; после D-015 и порядкового ограничения — 1.8, цель 1.3–1.5). Остаток
неоднозначности закрывает бинарный признак «на отметке 0 и ниже» против «выше
отметки 0». Q&A называет определение стадии по виду объекта «пунктом 1
выполнения задачи» (22:16).

В макете этому негде появиться. Нужны два места, оба дешёвые:
- строка в таблице этапов (фрейм 5): «Признак сцены: подземная часть —
  согласуется с техникой»;
- блок на карточке отклонения (7): «Сцена согласуется / расходится» — расхождение
  двух независимых сигналов само по себе сильный аргумент на защите.

### 5.4 Блокировка импорта при пересечении окон этапов (фрейм 2)

«Если окна этапов пересекутся, дальше пройти нельзя, пока их не объединят».
Реальный КСГ почти всегда содержит параллельные работы, а на вход по Q&A 41:49
подаётся файл заказчика с датами. Жёсткая блокировка превращает импорт чужого
файла в тупик прямо на демо.

Порядковое ограничение из D-015 нужно логике сопоставления (этап не может
подтвердиться раньше уже подтверждённого), а не импортёру. Предложение:
пересечение окон — **предупреждение** с кнопкой «объединить», проход дальше
разрешён.

### 5.5 Решение инженера по гипотезе (фрейм 7а)

`docs/product.md` §9 и §11: вывод сервиса — только для чтения, подтверждение и
отклонение отклонений **не входит в MVP**. Фрейм 7а вводит именно это.

Здесь я за то, чтобы **поменять product.md, а не макет**: человек в контуре
ровно на том выводе, который мы сами называем самым слабым (D-007: суждение об
активности выносится в 22% случаев, для кранов — никогда), — это не уступка, а
правильная форма честности. Условия: решение только для гипотез, итог по объекту
не меняется, решение хранится по ключу (объект, этап, тип, окно) и переживает
пересчёт методики — на макете это уже написано верно.

## 6. Придирки по фреймам

### 6.1 Верхний ряд (1, 2, 3, 3а, 4, 4а)

- **1.** Сквозной список отклонений по всем стройкам — за рамками MVP по
  `product.md` §11, но полезен как история масштабирования; оставить.
- **1.** В списке отклонений карточки ведут на `Site`, а не на карточки
  отклонений — в кликабельном прототипе жюри это заметит.
- **2.** «Нечёткое сопоставление · 74%» со справочником работ — хорошая деталь,
  прямо отвечает на вопрос «как вы привязались к нашему перечню».
- **3.** На всех пяти этапах ровно один комплект. При этом «ИЛИ»-комплекты —
  витрина методики и в `product.md`, и в контракте (плиту бетонируют либо
  автобетононасосом, либо башенным краном). Показать этап с двумя комплектами
  ничего не стоит и снимает половину вопросов про глубину методики.
- **3.** Нет редактирования **неожиданной техники** (`unexpected` в контракте),
  хотя «появление техники, не соответствующей этапу» — обязательная функция по
  ТЗ, и отклонение такого типа на фрейме 5 есть. Правило, породившее его,
  пользователю не видно и не правится.
- **3.** «Обычно N» с оговоркой «отставание в днях по количеству не считается» —
  точное попадание в Q&A 11:51 (количество техники не задаётся).
- **4.** Привязка зоны к **камере**, а не к площадке, закрывает возражение E7
  (зона не переносится между ракурсами). Это содержательное решение, а не
  оформление, — его стоит проговорить на защите.
- **4/4а.** Отличаются одной строкой состояния (открыт диалог). Как два артборда
  — нормально; в коде это один экран.

### 6.2 Нижний ряд (5, 6)

- **5.** Колонка «Факт по маркеру» — самое ценное в таблице: показывает, **чем**
  измерен факт, а не только результат.
- **5.** Нет ни одного примера `Не наблюдалось` и нет вида для будущих этапов
  (§4.3).
- **5.** Нет таймлайна план/факт. Это единственное, чего не хватает экрану,
  чтобы «за минуту понять» не только итог, но и картину целиком; см. §7.
- **5.** Чип «Наблюдаемость высокая» никуда не ведёт. Требование Q&A 13:01 —
  показать, **какой участок вне контроля**. Сейчас ответить нечем.
- **6.** Разбивка «по дням → по камерам → ленты кадров» правильная: это ровно
  единица сопоставления из контракта (наблюдение за дату), а не кадр.
- **6.** Лента «Без даты» с групповой правкой времени клипа — хорошо; 7 кадров
  из 126 не теряются молча. Совпадает с наблюдаемостью: на выданных данных ключ
  «(площадка, дата)» есть только у 47 кадров из 100.

### 6.3 Фреймы 7 и 7а — отвечаю на прямой вопрос

**Оставить, не переделывать.** Это самая сильная часть макета относительно
критериев: «качество предупреждений: содержательность, понятность и

Что поправить:

1. **Это один экран в двух режимах, а не два экрана.** Отличия гипотезы:

3. **«Важность»** — нового понятия нет ни в контракте, ни в `product.md`.

Весов в ТЗ нет, поэтому шкала 1–5 по каждому подпункту. Два столбца: **сейчас**
(макет + модель `mocs_mix`, бэкенд без домена) и **потолок** (если фреймы 1–7а
реализованы, ML подключён, правки §5 и §7 внесены).

| Критерий | Сейчас | Потолок | Чем обосновано |
|---|---|---|---|
| 8.1 Идея решения | 4 | 4,5 | Методика с источниками ГЭСН, маркерная техника, границы вывода, различение «не начат / не наблюдалось» — глубже типового «этап → ищем экскаватор» |

| 8.2 Скорость | 3 | 4 | Инференс на GPU — порядка 12 мс на кадр (`CONTRACTS.md`, `speed_ms`), но сквозного тракта нет и пользователю ничего не показано |
| 8.3 Качество распознавания | 3 | 3,5 | mAP50 0.426, полнота 0.56. Честно средне; узкое место — полнота, рычаг только внешние данные (E12, E13) |
| 8.3 Логика сопоставления | 4,5 | 5 | Сильнейшая часть: правило → источник → доказательство за два перехода |

**Среднее: 3,5 сейчас против 4,4 потолка.**

Главный вывод оценки: **узкое место сейчас не макет и не модель, а то, что между
ними ничего нет.** Дельта между «сейчас» и «потолком» почти целиком лежит в трёх
пунктах — интерфейс, полнота, качество кода, — и все три закрываются не
исследованием, а сборкой: бэкенд-домен по контрактам + фронт по этим десяти
фреймам + подключение `mocs_mix_best.pt` в тракт.

Улучшение детектора при этом почти не двигает балл: E12 показал, что рост
точности с 0.28 до 0.61 не изменил число совпавших статусов, а E14 — что рост
mAP на 0.077 оставил статусы теми же 8/10. Предел задаёт методика и полнота
наблюдений, а не модель.
