# One-pager: сервис контроля стройплощадки по снимкам

## 1. Контекст и цель

Сервис сравнивает то, что видно на снимках со стройплощадки, с календарным графиком работ и говорит, идёт объект по графику или отстаёт. Первый заказчик — Департамент градостроительной политики Москвы.

Сегодня такой контроль ведут вручную: смотрят камеры глазами, звонят подрядчику, оценивают на глаз. Это долго, субъективно и не позволяет реагировать вовремя.

MVP: одна стройка, внешние работы, этапы, которые видно по крупной технике. Вход — отдельные снимки и календарный график таблицей. Видео и потоковая обработка не предусмотрены.

**Цель MVP:** инженер заводит стройку с графиком, загружает снимки за дату и получает статус по каждому этапу с объяснением и снимками-доказательствами. Там, где данных не хватает, сервис говорит об этом прямо, а не выдаёт догадку за вывод.

## 2. Сценарии MVP

**Завести стройку**
Инженер создаёт объект, загружает календарный график таблицей, проверяет результат импорта.

**Настроить методику**
Инженер смотрит правила «этап работ → необходимая техника», видит источник каждого требования и правит их под свой объект.

**Загрузить снимки за дату**
Инженер загружает снимки. Сервис находит технику, собирает из кадров одно наблюдение за дату и показывает, что распознал и насколько хорошо просматривалась площадка.

**Прочитать состояние объекта**
Инженер видит таблицу статусов по всем этапам графика, вывод «отставание или соответствие» и отчёт о ходе работ.

**Разобраться в отклонении**
Инженер открывает карточку отклонения: что ожидалось, что наблюдается, на каких снимках, насколько сервис уверен и чего он утверждать не вправе.

## 3. Основные сущности и механики

**Стройка** — объект контроля. Хранит календарный график, набор правил и загруженные снимки. Всё состояние объекта выводится из этих трёх вещей.

**Календарный график** — перечень этапов работ с плановыми датами, загружается таблицей. Техники в графике нет: связь «этап → техника» задаётся отдельно, методикой.

**Методика «этап работ → техника»** — набор правил и центральный артефакт решения. Для каждого этапа заданы допустимые комплекты техники: комплекты между собой по «ИЛИ» (плиту бетонируют либо автобетононасосом, либо башенным краном), внутри комплекта по «И». У каждой машины указана обязательность — нормативная, со ссылкой на расценку ГЭСН, или логическая, обязательная по смыслу работы, но в норму не входящая (самосвал, автобетоносмеситель). Логическое требование не может быть единственным доказательством этапа. Этапы без крупной техники помечены как непроверяемые.

**Снимок** — отдельное изображение с датой и привязкой к стройке. Дата приходит из метаданных, распознаётся со штампа в кадре, выводится по соседним снимкам серии или вводится вручную. Источник даты хранится и показывается: инженер должен видеть, что пришло от камеры, а что выведено сервисом.

**Наблюдение за дату** — все снимки одной стройки за один день, сведённые в одну картину. Состав техники — объединение по кадрам, количество — максимум по кадрам, а не сумма: одна машина, снятая с пяти точек, остаётся одной машиной. Без этого техника, попавшая в один ракурс из пяти, считалась бы отсутствующей.

**Наблюдаемость** — насколько площадка вообще просматривалась: сколько кадров, какие ракурсы, есть ли закрытые зоны и слишком мелкие объекты. При низкой наблюдаемости сервис воздерживается от вывода вместо ложного «работы не ведутся».

**Работа или простой** — признак техники на уровне наблюдения, а не отдельного кадра. Выводится из изменения сцены между соседними датами и положения машины относительно рабочей зоны. По одному кадру действие не определяется, и при нехватке оснований сервис ставит «неизвестно».

**Статус этапа** — основной вывод сервиса: опережение, в графике, отставание, не начат, не наблюдалось, не проверяется по технике. Различать «не начат» и «не наблюдалось» обязательно: первое — утверждение о стройке, второе — о наших данных. Смешивать их значит выдавать отсутствие снимков за отсутствие работ.

**Отставание в днях** — не прогноз модели, а измеренный сдвиг между плановой границей и фактическим наблюдением. Его точность не выше частоты съёмки, и сервис это показывает.

**Отклонение** — объяснение к статусу: нужной техники нет, техника не соответствует этапу, набор техники не сходится с плановым этапом, между датами ничего не изменилось, данных давно нет, техника простаивает, машина вне рабочей зоны. Последние два — гипотеза, а не нарушение.

**Границы вывода** — у каждого отклонения есть формулировка того, что сервис утверждать не вправе. Например: отсутствие самосвалов на снимках не доказывает остановку вывоза грунта — вывоз мог идти вне времени съёмки.

## 4. Сценарий 1: завести стройку

**Цель:** появился объект с графиком, по которому можно что-то проверять.

1. Инженер создаёт стройку: название, адрес или условное обозначение.
2. Загружает календарный график таблицей: этапы работ с плановыми датами начала и окончания.
3. Сервис разбирает файл и показывает результат: сколько этапов распознано, у скольких есть даты, какие строки разобрать не удалось.
4. Инженер видит, какие этапы проверяются по технике, а какие помечены как непроверяемые, и почему.
5. Если дат в файле нет, инженер задаёт их вручную для этапов, которые хочет контролировать.

**Критерий успеха:** инженер понимает, что из графика сервис сможет проверить, а что нет, ещё до загрузки снимков.

## 5. Сценарий 2: настроить методику

**Цель:** связь «этап → техника» явная, проверяемая и подходит этому объекту.

1. Инженер открывает правила стройки. По умолчанию подставлен базовый набор.
2. Для каждого этапа видит допустимые комплекты техники, обязательность каждой машины и источник: номер расценки для нормативных требований, пометку «по смыслу работы» для логических.
3. Правит под свой объект: добавляет или убирает машину, меняет минимальное количество, добавляет альтернативный комплект.
4. Помечает этап как непроверяемый, если на его объекте этап не даёт видимой техники.
5. Сохраняет. Изменение правил пересчитывает статусы по уже загруженным снимкам — заново загружать ничего не нужно.

**Критерий успеха:** по любому выводу сервиса можно за два шага дойти до правила, которое его породило, и до источника этого правила.

## 6. Сценарий 3: загрузить снимки за дату

**Цель:** снимки превращаются в одно понятное наблюдение за дату.

1. Инженер выбирает стройку и загружает снимки — по одному или пачкой.
2. Сервис определяет дату каждого снимка: из метаданных, со штампа в кадре, по соседям в серии или спрашивает инженера.
3. Инженер видит источник даты по каждому снимку и может поправить дату вручную.
4. Сервис находит технику и показывает кадры с рамками и подписями классов.
5. Снимки одной даты сводятся в наблюдение: какая техника на площадке и сколько её — с пометкой «не менее», потому что счёт идёт по максимуму среди кадров.
6. Сервис показывает наблюдаемость: сколько кадров, какие ракурсы, были ли зоны вне обзора. При низкой наблюдаемости выводится предупреждение, что участок вне контроля и данные требуют проверки.
7. Снимки без определённой даты не теряются: они собраны в отдельный список и видны как проблема с данными.
8. Статусы этапов пересчитываются с учётом нового наблюдения.

**Критерий успеха:** инженер видит, что сервис распознал, откуда взялась дата и насколько площадка просматривалась, — до того, как читает выводы.

## 7. Сценарий 4: прочитать состояние объекта

**Цель:** за минуту понять, идёт объект по графику или нет, и где именно проблема.

1. Инженер открывает стройку.
2. Видит итог: отставание или соответствие графику, и на какой срок.
3. Видит таблицу статусов по всем этапам — включая те, по которым наблюдений нет, и те, что по технике не проверяются.
4. По этапу с отставанием видит срок, даты наблюдений, на которых основан вывод, и уровень уверенности.
5. Видит отчёт о ходе работ: что идёт с отставанием, что в графике, что с опережением.
6. Переходит от любого этапа к отклонениям, которые его объясняют.

**Критерий успеха:** на вопрос «мы отстаём?» инженер отвечает не открывая снимки, на вопрос «почему вы так решили?» — за один переход.

## 8. Сценарий 5: разобраться в отклонении

**Цель:** отклонение либо убеждает инженера, либо честно показывает свои пределы.

1. Инженер открывает карточку отклонения.
2. Видит тип отклонения, этап и период, к которым оно относится.
3. Видит сравнение: что ожидалось по правилу и что наблюдается.
4. Видит снимки-доказательства с рамками на технике.
5. Видит правило, которое сработало, и его источник.
6. Видит уровень уверенности и наблюдаемость зоны за этот период.
7. Видит формулировку границ: чего это наблюдение не доказывает.

**Критерий успеха:** по карточке инженер может либо действовать, либо понять, каких данных не хватает, — но не может принять догадку сервиса за факт.

## 9. Доступы MVP

Одна роль без ролевой системы:

* **Инженер / руководитель стройки** — заводит стройки, загружает графики и снимки, правит методику, читает статусы и отклонения.

Вывод сервиса — только для чтения: инженер не выставляет статус этапа вручную, не подтверждает и не отклоняет отклонения. Он влияет на вывод через вход — график и правила.

**На будущее:** аналитик департамента со сводной картиной по городу, разделение прав на правку методики, организации и объекты в подчинении.

## 10. Если MVP собран раньше срока

Порядок — по отдаче на затраты. Каждый пункт самодостаточен и не ломает основные сценарии.

* **Паспорт наблюдаемости площадки** — сервис по загруженным снимкам сам считает, какие зоны просматриваются и где обзор теряется, и выдаёт рекомендации по установке камер для этого объекта. Требование ТЗ, выполненное работающей функцией, а не пересказом норм.
* **Таймлайн план/факт** — этапы полосами по времени, поверх даты наблюдений, цветом статус. Всё состояние объекта на одном экране.
* **Стадия по виду самого объекта** — второй, независимый от техники способ определить этап. Два сигнала либо сходятся, либо дают честное расхождение.
* **Режим сверки** — те же правила на ручной разметке и на выводе распознавания, рядом. Видно, какие выводы ломает распознавание, а какие методика.
* **Отчёт одной кнопкой** — сводка по объекту за период, которую инженер отправляет дальше.

## 11. Не входит в MVP

* Видео и потоковая обработка — только отдельные снимки.
* Автоматическое получение снимков с камер и определение площадки по изображению.
* Правка вывода сервиса человеком: ручные статусы, подтверждение и отклонение отклонений.
* Контроль охраны труда, СИЗ, посторонних на площадке, складирования материалов.
* Внутренние работы, не определяемые по крупной технике.
* Сводный уровень: несколько объектов, карта строек, аналитика по подрядчикам.
* Прогноз сроков моделью — считается только измеренный сдвиг по наблюдениям.
* Уведомления, рассылки, интеграции с внешними системами заказчика.

## 12. Definition of Done для MVP

MVP считается успешным, если:

1. Инженер заводит стройку, загружает график таблицей и видит, какие этапы сервис сможет проверить по технике.
2. Инженер видит правила «этап → техника» с источниками и может их поправить; правка пересчитывает выводы без повторной загрузки снимков.
3. Инженер загружает снимки, видит распознанную технику на кадрах и сведённое наблюдение за дату с честным источником даты.
4. Сервис показывает таблицу статусов по всем этапам и вывод «отставание или соответствие» с отставанием в днях.
5. Статусы «не начат» и «не наблюдалось» различаются и объясняются пользователю.
6. Для техники определяется работа или простой, а при нехватке оснований ставится «неизвестно».
7. Карточка отклонения содержит ожидание, наблюдение, снимки-доказательства, сработавшее правило, уровень уверенности и границы вывода.
8. При низкой наблюдаемости сервис выводит предупреждение вместо вывода о ходе работ.
9. Решение демонстрируется на наборе примеров, покрывающем все статусы и типы отклонений, в разные сезоны и с разных ракурсов.
