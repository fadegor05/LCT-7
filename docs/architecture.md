# Архитектура: сервис контроля стройплощадки по снимкам

> Статус: каркас. Разделы 2–6 — заглушки, заполняются после согласования сценариев. Здесь зафиксировано то, что уже принято и от чего зависят несколько человек: требования, словари значений и правила вывода.

## 1. Требования

### 1.1. Функциональные требования

**UC-1: Завести стройку**
Инженер создаёт объект и загружает календарный график таблицей (Excel/CSV): этапы работ с плановыми датами начала и окончания. Парсер разбирает файл, показывает результат импорта и помечает этапы, непроверяемые по технике. Если дат в файле нет, инженер задаёт их вручную.

**UC-2: Настроить методику**
Инженер просматривает и правит правила «этап работ → необходимая техника»: комплекты техники, минимальные количества, обязательность, признак проверяемости. Правка правил пересчитывает статусы по уже загруженным снимкам без повторной обработки изображений.

**UC-3: Загрузить снимки за дату**
Инженер загружает снимки. Сервис определяет дату каждого снимка, находит на нём технику, сводит снимки одной даты в наблюдение и пересчитывает статусы этапов. Снимки без определённой даты выделяются в отдельный список.

**UC-4: Прочитать состояние объекта**
Инженер получает таблицу статусов по всем этапам графика, итоговый вывод «отставание или соответствие» с отставанием в днях и отчёт о ходе работ.

**UC-5: Разобраться в отклонении**
Инженер открывает карточку отклонения: тип, этап, период, ожидание против наблюдения, снимки-доказательства, сработавшее правило с источником, уровень уверенности, наблюдаемость и границы вывода.

### 1.2. Нефункциональные требования

Числа MVP — ориентир под демонстрацию, целевые — оценка под эксплуатацию у заказчика. Уточняются при проектировании.

| Параметр | MVP | Целевой продукт |
|---|---|---|
| Строек | 1–15 | сотни |
| Снимков на стройку за дату | 5–20 | 50+ |
| Этапов в графике | 10–40 | 100+ |
| Обработка снимка | приемлемо на CPU ноутбука | GPU на сервере |
| Задержка выдачи предупреждения | секунды после обработки | близко к реальному времени |
| Пересчёт статусов после правки правил | без повторной обработки изображений | то же |
| Развёртывание | Docker + инструкция | он-премис у заказчика |

Ограничения, заданные постановщиком: вход — только отдельные изображения, видео и потоковые данные не предусмотрены; метаданные снимков (дата, время, ID объекта и камеры) не гарантируются; других каналов входа, кроме фотофиксации, нет; демонстрация идёт на обычном ноутбуке, GPU не обязателен; скорость обработки — отдельный критерий оценки.

## 2. Границы системы

### Внешние участники и системы

* **Инженер / руководитель стройки** — единственная роль MVP: заводит стройки, загружает графики и снимки, правит методику, читает выводы.
* **Источник снимков** — в MVP загрузка файлов вручную. В целевом виде — камеры площадки, откуда дата, время и идентификатор объекта приходят вместе с кадром.
* **Справочники норм (ГЭСН)** — внешний источник обоснования правил. В систему попадают как ссылки в правилах, а не как интеграция.

## 6. Детализация компонентов

### 6.1. Раскладка бэкенда

| Путь | Назначение |
|---|---|
| `app/core/` | инфраструктура: `settings.py`, `database.py` (`Base`), `repository.py` (`BaseRepository`), `security.py` |
| `app/plugins/` | сквозные вещи: `di.py` (Dishka-контейнер), `routing.py`, `exceptions.py` |
| `app/adapters/` | внешние системы: ML, справочные данные ГЭСН |
| `app/domains/<домен>/` | один домен — один плоский каталог: `models.py`, `schemas.py`, `repository.py`, `service.py`, `router.py`, `provider.py` |
| `app/models.py` | единая точка импорта ORM-моделей всех доменов — по ней Alembic autogenerate видит схему |
| `app/main.py` | сборка приложения: подключение роутеров, DI-контейнера, обработчиков ошибок |

`core/`, `adapters/` и `plugins/` доменами не являются: в них нет `router.py`/`service.py`, промежуточного уровня `modules/` нет — домены лежат прямо в `app/domains/`.

### 6.2. Состав домена

Все шесть файлов не обязательны: файл опускается, если домену он не нужен (например, `utility` — без моделей и репозитория, только `schemas.py` и `router.py`).

| Файл | Ответственность |
|---|---|
| `models.py` | ORM-модели (SQLAlchemy) |
| `schemas.py` | Pydantic-контракты запросов/ответов |
| `repository.py` | запросы к БД поверх `BaseRepository` |
| `service.py` | бизнес-логика домена, владеет `AsyncSession` и вызывает `commit()` |
| `router.py` | HTTP-эндпоинты, сборка схем из результата сервиса |
| `provider.py` | DI-провайдер домена (репозиторий + сервис) |

### 6.3. Скоупы DI

| Scope | Что живёт |
|---|---|
| `Scope.APP` | настройки, engine, sessionmaker, клиенты внешних систем, парсеры без состояния, кэши справочников |
| `Scope.REQUEST` | `AsyncSession`, репозитории, сервисы |

Каждый домен регистрирует свой `provider.py` в `create_container()` (`app/plugins/di.py`).

### 6.4. Как добавить домен

1. Создать `app/domains/<домен>/` по образцу `user/` — только нужные из шести файлов.
2. Зарегистрировать роутер в `app/plugins/routing.py`.
3. Зарегистрировать провайдер в `create_container()` (`app/plugins/di.py`).
4. Дописать импорт моделей домена в `app/models.py` — иначе Alembic их не увидит.
5. Сгенерировать миграцию: `uv run alembic revision --autogenerate -m "..."`.

## 7. Словари значений

Значения ниже используются в контрактах, интерфейсе и документации. Меняются только согласованно: правка ломает чужой код.

### 7.1. Статус этапа

| Значение | Когда |
|---|---|
| Опережение | работы этапа наблюдаются раньше планового начала |
| В графике | наблюдения согласуются с плановым окном |
| Отставание | работы наблюдаются после плановой даты окончания |
| Не начат | плановое начало прошло, техника этапа не наблюдается |
| Не наблюдалось | наблюдений в окне нет: снимков не было или площадка не просматривалась |
| Не проверяется по технике | этап не определяется по крупной технике |

Правило вывода: «не начат» — утверждение о стройке, «не наблюдалось» — о наших данных. Смешивать их нельзя.

### 7.2. Типы отклонений

| Тип | Смысл |
|---|---|
| Нет нужной техники | техники этапа нет или её меньше требуемого |
| Лишняя техника | наблюдается техника, которой на этапе не ждём — гипотеза |
| Несоответствие этапу | набор техники не сходится с плановым этапом |
| Нет прогресса | между соседними датами сцена не изменилась |
| Данные устарели | по объекту давно нет снимков |
| Простой техники | техника присутствует, но не работает |
| Вне рабочей зоны | машина вне своей зоны — гипотеза, не нарушение |

### 7.3. Уверенность

Три уровня: высокая, средняя, низкая. Не число. Уверенность распознавания не переживает сведение по кадрам, датам и правилам — три честных уровня лучше двух знаков после запятой, за которыми ничего не стоит.

### 7.4. Источник даты снимка

| Значение | Откуда |
|---|---|
| Канал | пришла вместе с кадром от камеры |
| Метаданные | из EXIF файла |
| Штамп | распознана со штампа в кадре |
| По соседям | выведена по соседним снимкам серии |
| Вручную | введена инженером |

Источник обязателен и показывается в интерфейсе: инженер должен отличать то, что пришло от камеры, от того, что вывел сервис.

### 7.5. Обязательность техники в правиле

| Значение | Смысл |
|---|---|
| Нормативная | машина есть в разделе «Машины и механизмы» расценки ГЭСН, указывается номер |
| Логическая | обязательна по смыслу работы, но в норму не входит (самосвал, автобетоносмеситель) |
| Вспомогательная | может присутствовать, отсутствие не является отклонением |

Логическое требование не может быть единственным доказательством этапа.

### 7.6. Активность техники

Три значения: работает, простаивает, неизвестно. Определяется на уровне наблюдения за дату, не отдельного кадра: по изменению сцены между соседними датами и положению машины относительно рабочей зоны. При нехватке оснований — «неизвестно»; догадка недопустима.

## 8. Правила вывода, обязательные к соблюдению

Эти правила не зависят от выбранной архитектуры и должны выполняться в любой реализации.

1. **Количество техники за дату — максимум по кадрам, не сумма.** Одна машина, снятая с пяти точек, остаётся одной машиной. Полученное число — нижняя оценка, в интерфейсе подаётся как «не менее».
2. **Кадр без находок остаётся в данных.** Отсутствие техники на снимке — тоже наблюдение.
3. **Снимок без даты или без привязки к стройке не отбрасывается молча.** Он попадает в отдельный список как проблема с данными.
4. **При низкой наблюдаемости вывод о ходе работ не делается.** Вместо него — предупреждение, что участок вне контроля.
5. **Отставание в днях — измеренный сдвиг, а не прогноз модели.** Его точность ограничена частотой съёмки, и это указывается.
6. **У каждого отклонения есть границы вывода** — формулировка того, что оно не доказывает.
7. **Вывод сервиса не правится пользователем.** Влияние на вывод — только через график и правила.
