# Интеграция ML в бэкенд

Для разработчиков бэкенда. Что запустить, что вызвать, что придёт в ответ и где
проходят границы ответственности.

Смежные документы: `CONTRACTS.md` — форматы обмена, `MODEL_CARD.md` — что за
модель и чего она не умеет, `../README.md` — устройство папки.

---

## 1. Что делает ML-часть

Три шага, каждый читает выход предыдущего:

```
снимок ──> детекции ──> состояние площадки ──> статусы этапов и алерты
          (детектор)     (site_state)          (match_schedule)
```

| шаг | что делает | где живёт |
|---|---|---|
| детекции | находит технику на кадре, 25 классов | HTTP-сервис, см. §2 |
| состояние | сводит кадры по паре «площадка + дата», убирает дубли | `tools/site_state.py` |
| статусы | сопоставляет с календарным планом, выдаёт вердикты и алерты | `tools/match_schedule.py` |

**Первый шаг — сервис, второй и третий — скрипты.** Так сделано намеренно:
детекция требует модели в памяти и вызывается на каждый кадр, а сведение и
сопоставление — дешёвые операции над JSON, которые логично запускать по
расписанию или по кнопке в интерфейсе.

---

## 2. Сервис детекции

### Запуск

```bash
docker build -t lct7-ml ml/
docker run -d --name lct7-ml -p 8000:8000 \
    -v "/path/to/weights:/weights:ro" \
    -e WEIGHTS=/weights/mocs_m_best.pt \
    lct7-ml
```

Веса в образ не входят: 42 МБ и лицензия AGPL. Берутся командой
`python tools/fetch_weights.py`. Нужны `HF_REPO` и `HF_TOKEN` — скопируйте `ml/.env.dist` в `ml/.env` и заполните; токен у каждого свой.

Переменные окружения:

| переменная | по умолчанию | зачем |
|---|---|---|
| `WEIGHTS` | `/weights/mocs_m_best.pt` | какие веса грузить |
| `MAX_UPLOAD_BYTES` | 20971520 (20 МБ) | предел размера кадра |
| `YOLO_CONFIG_DIR` | `/tmp` | иначе ultralytics пишет в домашний каталог, которого в контейнере нет |

Модель грузится и прогревается на старте — это занимает до полутора минут на
процессоре. До готовности `/health` отвечает, но `/detect` вернёт 503.
`HEALTHCHECK` в образе учитывает это через `start-period=90s`.

### Методы

| метод | ответ |
|---|---|
| `GET /health` | `{"status": "ok", "model_loaded": true}` |
| `GET /meta` | какие веса, пороги и устройство отвечают — пишите в журнал вместе с результатом |
| `POST /detect` | детекции по одному кадру, формат ниже |
| `POST /report` | статусы этапов и алерты по площадкам, см. §4 |
| `POST /ask` | вопрос по отчёту на естественном языке; ответ с пометкой `verified` |
| `GET /docs` | автодокументация OpenAPI |

### Запрос и ответ

```bash
curl -X POST -F "file=@frame.png" http://localhost:8000/detect
```

```json
{
  "image": "frame.png",
  "width": 1080,
  "height": 809,
  "speed_ms": {"preprocess": 3.1, "inference": 41.2, "postprocess": 1.4, "total": 64.7},
  "detections": [
    {"class_raw": "drilling_rig", "class_ours": "drilling_rig",
     "conf": 0.88, "bbox": [0.5396, 0.0, 0.6227, 0.6529]}
  ]
}
```

**`bbox` — доли кадра, порядок `[x1, y1, x2, y2]`, начало координат в левом
верхнем углу.** Не пиксели: снимки приходят разного размера, а доли не требуют
знать размер при сравнении. Обратный перевод — умножением на `width` и `height`,
которые лежат рядом.

### Коды ошибок

| код | когда | что делать |
|---|---|---|
| 400 | пустой файл | не повторять |
| 413 | файл больше лимита | уменьшить или поднять `MAX_UPLOAD_BYTES` |
| 422 | не читается как изображение | не повторять, писать в журнал имя файла |
| 503 | модель ещё грузится | повторить через 10–20 с |

Сервис переживает битые файлы: после 422 продолжает работать, проверено.

## 3. Полная цепочка

### Через API (для бэкенда)

Два запроса. Первый — детекции по каждому кадру, второй — отчёт по накопленным
детекциям. Данные передаются телом запроса: у бэкенда они в базе, гонять их
через файлы незачем.

```http
POST /report
{
  "observations": [
    {"image": "frame1.png", "site_id": "p08", "date": "2024-04-24",
     "width": 1080, "height": 809,
     "detections": [{"class_raw": "drilling_rig", "class_ours": "drilling_rig",
                     "conf": 0.88, "bbox": [0.54, 0.0, 0.62, 0.65]}]}
  ],
  "schedule": [
    {"site_id": "p08", "stage_code": "12.3.2", "stage_name": "Устройство свай",
     "planned_start": "2024-01-15", "planned_end": "2024-03-31"}
  ],
  "conf": 0.25
}
```

В ответе — структура из §4 плюс блок `summary`: сколько каких статусов и алертов
всего, для сводки в интерфейсе. В `meta` видно, сколько кадров пришло, сколько
использовано и сколько отброшено без площадки или даты.

Календарный план бэкенд берёт из своей базы либо получает из файла заказчика
через `tools/parse_schedule.py` (Excel и PDF из MS Project).

### Через скрипты (для исследования и отладки)

Детекции по всем кадрам собираются в один файл, дальше два скрипта:

```bash
# 1. детекции по папке (CLI-вариант того же, что делает сервис)
python tools/detect_finetuned.py <папка_с_кадрами> \
    --weights weights/mocs_m_best.pt --out data/processed/detections.json

# 2. свод по площадкам и датам
python tools/site_state.py --detections data/processed/detections.json \
    --sites data/reference/sites.csv --out data/processed/site_state.json

# 3. сопоставление с графиком
python tools/match_schedule.py --state data/processed/site_state.json \
    --schedule data/reference/schedule_demo.csv --rules configs/rules.json \
    -o data/processed/report.json
```

### Что нужно от бэкенда

| данные | формат | откуда |
|---|---|---|
| привязка кадра к площадке и дате | `sites.csv`: `image;date;site_id` | интерфейс или метаданные камеры |
| календарный план | `schedule.csv`: `site_id;stage_code;stage_name;planned_start;planned_end` | `tools/parse_schedule.py` из Excel или PDF заказчика |
| правила «этап → техника» | `configs/rules.json` | редактируется пользователем (D-009) |

**Дата и площадка обязательны.** Кадр без даты в анализ не попадает — это не
ошибка, а сознательное решение: без даты нельзя сказать, отстаёт этап или нет.
Такие кадры считаются и попадают в отчёт отдельным алертом `unusable_data`,
чтобы пользователь видел, что часть данных вне анализа.

## 4. Что приходит в отчёте

```json
{"sites": [{
  "site_id": "p08",
  "as_of": "2024-04-24",
  "observations": 3,
  "stages": [{"stage_code": "12.3.2", "stage_name": "Устройство свай",
              "status": "behind", "basis": "работы наблюдаются после плановой даты окончания"}],
  "equipment_engagement": [{"class": "drilling_rig", "observations": 48, "decided": 1,
                            "basis": "определённый ответ дан по 1 наблюдениям из 48 — меньше порога 10, доля не оценивается"}],
  "alerts": [{"type": "stage_behind", "stage_code": "12.3.2",
              "explanation": "Этап «Устройство свай» отстаёт на 24 дн. ...",
              "cannot_claim": "Отставание измерено по снимкам ..."}],
  "forecast": {"shift_days": 24,
               "planned_completion": "2024-09-30",
               "projected_completion": "2024-10-24",
               "stages": [{"stage_code": "12.3.6", "stage_name": "Монолит выше нуля",
                           "planned_end": "2024-09-30", "projected_end": "2024-10-24",
                           "shift_days": 24}],
               "basis": "наибольшая наблюдаемая задержка 24 дн. переносится ...",
               "assumption": "этапы считаются последовательными, задержка не нагоняется. Это верхняя оценка сдвига",
               "cannot_claim": "Срок не рассчитан по объёму выполненных работ ..."}
}]}
```

### Блок `forecast`

Отвечает на вопрос заказчика «когда закончат, если так пойдёт дальше»
(Q&A 12:52). Это **арифметика графика**: наибольшая измеренная задержка
переносится на этапы, которые должны были начаться после окончания
задержавшегося, и сдвигает плановое завершение.

| поле | что означает |
|---|---|
| `shift_days` | на сколько дней съезжает завершение площадки |
| `planned_completion` / `projected_completion` | дата по плану и с учётом сдвига |
| `stages` | какие этапы съезжают и на сколько |
| `assumption` | допущение о последовательности этапов — **показывать рядом с датой** |
| `cannot_claim` | что это не расчёт по объёму работ |

Когда задержавшихся этапов нет, приходит `{"shift_days": 0, "basis": ...}` —
блок всегда есть, отдельной проверки на `null` не нужно.

Прогноз — **верхняя оценка**: если подрядчик нагонит темп или пустит работы
параллельно, сдвиг будет меньше. В интерфейсе дату стоит подавать как «при
сохранении текущего темпа», а не как срок.

### Статусы этапов

| значение | смысл |
|---|---|
| `ahead` | работы наблюдаются раньше планового начала |
| `on_track` | наблюдения согласуются с плановым окном |
| `behind` | работы наблюдаются после планового окончания |
| `not_started` | плановое начало прошло, техника этапа не наблюдается |
| `not_observed` | наблюдений в окне нет — **утверждение о наших данных, не о стройке** |
| `not_checkable` | этап по технике не определяется (кровля, фасад, гидроизоляция) |
| `no_rule` | **кода этапа нет в методике** — пробел в настройке, а не вывод о стройке |

Различать последние четыре обязательно. Смешать `not_started` и `not_observed` —
значит выдать отсутствие снимков за отсутствие работ. Смешать `not_checkable` и
`no_rule` — значит спрятать ошибку настройки: план с чужой нумерацией этапов
целиком стал бы «не проверяется по технике», и сервис молча выглядел бы
работающим. Поэтому `no_rule` дополнительно поднимает алерт `unknown_stages` по
площадке.

### Типы алертов

`stage_behind`, `stage_not_started`, `stage_stalled`, `missing_equipment`,
`unexpected_equipment`, `no_progress`, `unusable_data`, `plan_invalid`,
`unknown_stages`.

Два последних — про **входные данные, а не про стройку**: `plan_invalid`
сообщает, сколько строк плана не разобрано и почему, `unknown_stages` — сколько
кодов этапов отсутствует в методике. Их стоит показывать отдельно от отклонений
по работам: это то, что чинится правкой плана или `configs/rules.json`.

### Что бывает с грязным планом

### Счётчики в `meta`, которые стоит показывать

| поле | зачем |
|---|---|
| `frames_in` / `frames_used` / `frames_unusable` | сколько кадров дошло до анализа; сумма двух последних равна первому |
| `plan_rows_in` / `plan_rows_used` / `plan_rows_rejected` | сколько строк плана дошло до анализа |
| `sites_without_plan` / `frames_without_plan` | **площадки, по которым есть снимки, но нет ни одной строки плана.** Их нет ни в одном отчёте — сравнивать не с чем. Если это не показать, для пользователя объект просто исчезает |

Сервис не отклоняет план целиком из-за одной ошибки: в присланном заказчиком
файле 13 строк содержали дату «30.02.2027». Битая строка выбрасывается поимённо,
повторяющиеся этапы сводятся в один (от самого раннего начала до самого позднего
окончания), а счётчики `plan_rows_in` / `plan_rows_used` / `plan_rows_rejected` в
`meta` показывают, сколько плана реально дошло до анализа. Площадка, у которой не
разобралась ни одна строка, **остаётся в ответе** — иначе предупреждение
исчезло бы вместе с ней.

**В каждом алерте есть поле `cannot_claim`** — что система на этих данных
утверждать не вправе. Его нужно показывать пользователю, а не прятать: это
защита и от неверных решений, и от вопроса «почему вам можно верить».

## 5. Границы: чего ML не делает

Эти пункты стоит держать в интерфейсе, чтобы не обещать лишнего.

1. **Не определяет, работает техника или простаивает, по одному кадру.** Это
   ненаблюдаемо: работа и простой различаются движением. Выдаётся доля
   наблюдений без признаков вовлечённости за период, с интервалом; при малом
   числе наблюдений — «доля не оценивается» (D-017).
2. **Не считает процент готовности объекта.** Без BIM это делается чек-листами,
   а не зрением (D-016).
3. **Не рассчитывает срок по объёму выполненных работ.** Объём по снимкам не
   измеряется. Блок `forecast` переносит измеренную задержку по графику и
   помечен как верхняя оценка — это не модель производительности подрядчика.
4. **Путает мобильный кран с буровой установкой** — 15 случаев на оценочной
   выборке. Проверено четырьмя способами, свойство задачи, а не дефект модели.
5. **Не работает с видео и потоком.** Вход — отдельные кадры.

## 6. Производительность и ресурсы

| | |
|---|---|
| один кадр, процессор | ~364 мс |
| один кадр, GPU | ~56 мс |
| память процесса | около 500 МБ |
| размер образа | 2.46 ГБ (почти всё — PyTorch) |

При продуктовом режиме «кадр раз в 20–30 минут с камеры» одного ядра хватает на
сотни камер. GPU не обязателен.

**Известный риск развёртывания:** Docker Hub из сети разработки недоступен
(TLS timeout, зеркала gcr/timeweb/huecker тоже). Образ собирался на локальном
кеше базового слоя. На сервере понадобится доступное зеркало или приватный
реестр — проверьте это заранее.
