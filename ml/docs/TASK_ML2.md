# Задачи второму ML-инженеру

Файл самодостаточный: чтобы начать, читать весь репозиторий не нужно. Ниже —
контекст за пять минут, путеводитель по документам с пометками, что именно там
важно, и три задачи с критериями готовности.

---

## 1. Контекст за пять минут

**Кейс.** Департамент градостроительной политики Москвы: сервис, который по
снимкам со стройплощадок определяет технику, сопоставляет её с этапами
календарного графика и выдаёт отклонения. Сдача 29.09, 23:59 МСК.

**Как оценивают.** Числовой метрики и лидерборда **нет**. Судят эксперты по
пяти критериям: подход и логика сопоставления, качество кода и архитектуры,
качество распознавания и устойчивость, полнота требований и документация, питч.
Отдельным пунктом — **скорость обработки**, причём демонстрация идёт на обычных
ноутбуках, без GPU.

Практический вывод: +2 mAP не стоят ничего, если ими нельзя объяснить связь
техники с этапом работ. Но и распознавание должно быть приличным — «качество
распознавания и устойчивость решения на разнообразных примерах» это отдельный
критерий, и это как раз ваша часть.

**Данные — четыре факта, которые определяют работу:**

1. Организаторы выдали **100 неразмеченных снимков** — фоторепортажи с разных
   московских строек 2023–2026 (съёмка с земли, со зданий, с дрона).
2. Рекомендованный ими Kaggle-датасет — **кадры стационарных камер**
   видеонаблюдения, 19 982 штуки, осень–зима 2023/24, разметка YOLO.
3. То есть **два разных домена**. Учимся на CCTV, проверяемся на фоторепортажах.
4. Двух классов из обязательного списка ТЗ в данных почти нет: **каток — 4
   объекта**, **бульдозер — 0**. Зато на снимках организаторов доминируют
   буровые установки и башенные краны, которых в списке ТЗ нет вовсе.

**Разделение работы.** Логика (состояние площадки, сопоставление с графиком,
алерты) — на первом ML-инженере. Данные и обучение — на вас. Пересечений почти
нет, файлы разные.

## 3. Задача 1 — подготовка обучающих данных

**Зачем.** Без этого нельзя дообучать: Kaggle в нынешнем виде даёт завышенную
оценку из-за утечки по камерам, а APOCE лежит в другом формате.

### 1.1 Прореживание Kaggle

Архив: `data/external/kaggle_construction_equipment.zip`, 17.5 ГБ,
`train/images` + `train/labels`, `valid/…`, разметка YOLO (5 токенов в строке).

В именах файлов зашиты камера и время:
`camera_6.201_2024-01-05T16_42_20_236+03_00.jpg`. Есть и другой формат
префикса — `238_12_24_27_053979-2023-09-22.jpg`. Всего около 20 камер.

Кадры одной камеры идут подряд и почти одинаковы. Оставить не чаще одного кадра
на камеру за N минут; N подобрать так, чтобы осталось **3–5 тысяч кадров**.

*Подчеркнуть:* прореживание по времени важнее, чем кажется. Без него модель
увидит один и тот же экскаватор на одной и той же парковке тысячу раз и выучит
фон, а не технику.

### 1.2 Свой сплит

Родной `train`/`valid` использовать нельзя. Нужен **leave-camera-out**: 2–3
камеры целиком в hold-out, остальные в обучение. Проверить, что пересечения по
камерам нет вообще.

### 1.3 Приведение классов

17 классов Kaggle → наша таксономия (таблица в `LABELING_SPEC.md` §8).
Отдельно решить и записать в `DECISIONS.md`:
- **`Gazelle`** (520 объектов, лёгкий фургон) — для этапов бесполезен, но это
  третий по частоте класс, и он будет конкурировать с грузовиками;
- **`Cleaning equipment`**, **`Tanker`**, **`Trailer`** — оставлять или сливать.

### 1.4 APOCE

`data/external/apoce/` — уже распакован. 928 изображений, разметка **COCO**
(`_annotations.coco.json` в каждом сплите), 7 классов.

*Подчеркнуть две вещи:*
- класс **`piling-machine` объединяет буровые установки и копры** — при слиянии
  с нашей таксономией эти два класса придётся схлопнуть в один, иначе разметка
  противоречива;
- это **строго надирная съёмка с дрона**, а наши кадры сняты с земли и со
  зданий. Одна и та же машина сверху и сбоку выглядит совершенно по-разному.
  Прирост от APOCE не предполагать, а измерить.

**Критерий готовности задачи 1:** единый датасет в одном формате, сплит по
камерам без пересечений, в `EXPERIMENTS.md` записаны число кадров и объектов на
класс после прореживания.

## 4. Задача 2 — дообучение

Три кандидата из `part_K`, сравнивать на одном сплите:

| Кандидат | Плюс | Минус |
|---|---|---|
| YOLO26 s/m | быстрее всех на CPU (87 / 220 мс при 640) | **AGPL-3.0**, и это распространяется на веса |
| RF-DETR S/M | Apache, лучше переносится на малые данные | официальных цифр для CPU нет, надо мерить |
| D-FINE / DEIM S/M | Apache, хороший баланс | меньше готовых удобств |

*Подчеркнуть:* решение по лицензии (D-001) ещё не принято командой. Поэтому
**держите детектор за отдельным интерфейсом** — чтобы смена семейства моделей не
переписывала пол-проекта.

**Что измерять:**
1. Качество на hold-out камерах Kaggle — это «в домене».
2. **Качество на 100 снимках организаторов** — это перенос CCTV → фоторепортажи,
   и это главное число. Разметку для них сделает первый ML-инженер; до неё
   оценивайте глазами по контакт-листам (`tools/make_contact_sheets.py`).
3. **Латентность на CPU**, 640 и 1280, через ONNX. По ТЗ это отдельный критерий.

**Отдельно проверить:** поднялись ли `drilling_rig`, `crawler_crane`,
`dump_truck` — те самые классы, что сейчас на уровне шума.

Проверить качество чужой разметки Kaggle глазами на 50 случайных кадрах:
пропуски, ошибки классов, границы рамок. Мы на ней учимся, а её никто не смотрел.

## 6. Чего не делать

- **Не обучать на 100 снимках организаторов** (D-006). Они — честная проверка.
- **Не гнаться за mAP на родном сплите Kaggle.** Он с утечкой, цифра будет
  красивой и бессмысленной.
- **Не ставить torch командой `pip install torch`** — получите сборку `+cpu`, и
  GPU молча не будет использоваться. Порядок установки описан в
  `requirements.txt`.
- **Не тратить время на классы, которых нет в данных** (каток, бульдозер) —
  их закроем своей разметкой.

## 7. Как отчитываться

Каждый прогон — запись в `EXPERIMENTS.md` по шаблону в конце файла:
вопрос, конфигурация, результат в цифрах, вывод, что дальше.

Работа в ветке, в `main` — через пулл-реквест. В `main` попадает только то, что
запускается.
