# Карточка модели: детектор строительной техники

Версия `mocs_m_best`, 22.09.2026. Документ отвечает на вопросы, которые возникнут
через месяц у того, кто найдёт файл весов на сервере.

## Что это

Детектор строительной техники на снимках площадок. Находит 25 классов; из них
семь **специфичных** — те, что однозначно указывают на этап работ (буровая
установка, копёр, установка «стена в грунте», асфальтоукладчик, грейдер,
автобетононасос, каток). Остальные универсальные: встречаются на многих этапах и
сами по себе этап не подтверждают.

Выход — рамки в долях кадра по контракту `docs/CONTRACTS.md` §1. Дальше по
цепочке: `site_state.py` сводит детекции по паре «площадка и дата»,
`match_schedule.py` сопоставляет с календарным планом.

## Известные ограничения

1. **Путает мобильный кран с буровой.** 15 ошибок в обе стороны на оценочной
   выборке. Причина — схожесть решётчатой стрелы и мачты. Пытались решить
   четырьмя способами (E12, E13, E18, E19): помогла только ёмкость модели.
2. **Теряет башенные краны**, полнота 0.38. Рамка получается большой и почти
   пустой — тонкая мачта на фоне неба.
3. **Грузовики на наших кадрах не измерены**: в оценочной выборке всего 2
   самосвала, цифра 0.198 статистически бессмысленна. На отложенном сплите MOCS
   (547 рамок) модель даёт AP50 0.715 — класс она умеет, но это другой домен, и
   `truck` там объединяет самосвалы с прочими грузовиками (E22).
4. **Бульдозер, каток, асфальтоукладчик** — в нашей оценочной выборке по 0–1
   примеру. На отложенном MOCS: бульдозер 0.827, каток 0.865 (E22); на московских
   фотоотчётах качество по-прежнему неизвестно.
5. **Не определяет, работает техника или простаивает.** Это принципиально
   ненаблюдаемо по одному кадру (D-017, research/part_N_activity.md).
6. **Обучена на осенне-зимних и весенних кадрах**, летних мало: в Kaggle их нет
   вовсе.

## Где взять веса

В git не хранятся: 42 МБ, а `.gitignore` исключает `*.pt`. Лежат в **приватном**
репозитории HuggingFace `Gatarez/lct7-construction-detector` — приватном потому,
что снимки организаторов и всё производное от них публичными быть не должны
(D-005).

```bash
python tools/fetch_weights.py            # PyTorch, 42 МБ
python tools/fetch_weights.py --onnx     # ONNX, 78 МБ
```

Нужен токен с правом чтения: `HF_TOKEN=...` в `ml/.env` или в переменных
окружения. Без токена скрипт скажет об этом прямо, а не упадёт с невнятной
ошибкой. ONNX-версия —
`weights/mocs_m_best.onnx`, 78 МБ, даёт те же детекции (mAP 0.459 против 0.470,
разница в пределах округления) и не требует Ultralytics в рабочем окружении.

## Лицензии

- **Ultralytics AGPL-3.0** — распространяется и на обученные веса. Репозиторий
  под AGPL-3.0 (D-001). Закрытое внедрение потребует коммерческой лицензии
  Ultralytics либо перехода на детектор под Apache (RF-DETR, D-FINE).
- **MOCS** — MIT. **APOCE** — MIT. **Kaggle CCTV** — CC0.
- ONNX-версия от Ultralytics не зависит в рантайме, но получена их кодом:
  вопрос о лицензии весов это не снимает.

## Запуск в контейнере

Проверено 24.09.2026: детекции в образе совпадают с хостом до четвёртого знака.

```bash
docker build -t lct7-ml:test ml/
docker run --rm -v "<путь>/ml/weights:/weights:ro" -v "<путь>/frames:/frames:ro" \
    -e YOLO_CONFIG_DIR=/tmp lct7-ml:test \
    python -m service.detector /frames/frame.png --weights /weights/mocs_m_best.pt
```

Что выяснилось при проверке и о чём легко забыть:

| | |
|---|---|
| Размер образа | **2.46 ГБ**, почти всё — PyTorch. На ONNX без ultralytics ужмётся примерно до 400 МБ |
| Системные пакеты | `libgl1`, `libglib2.0-0` — без них падает импорт OpenCV на чистом slim |
| `YOLO_CONFIG_DIR=/tmp` | Ultralytics пишет настройки в домашний каталог, которого в контейнере нет |
| Веса | монтируются томом, в образ не кладутся: 42 МБ в слое и лицензия AGPL на них |
| База образа | `python:3.11-slim`, а не 3.12: **Docker Hub из сети разработки недоступен** (TLS timeout на registry-1.docker.io и на зеркалах gcr, timeweb, huecker), 3.11 был в локальном кеше |

**Docker Hub недоступен — это риск для деплоя.** На сервере понадобится доступное
зеркало или приватный реестр, иначе образ не соберётся.

## HTTP-сервис

`service/app.py` — тонкая обёртка над `service/detector.py` на FastAPI (тот же
стек, что у бэкенда). Отдельным процессом, а не библиотекой внутри бэкенда:
модель держит в памяти около 500 МБ и грузится секунды, а бэкенд перезапускается
часто.

| метод | что делает |
|---|---|
| `GET /health` | жив ли сервис; модель не трогает, отвечает сразу |
| `GET /meta` | какие веса и пороги отвечают — для журнала бэкенда |
| `POST /detect` | кадр (multipart) -> детекции в формате контракта §1 |
| `GET /docs` | автодокументация OpenAPI |

Коды ошибок: 400 — пустой файл, 413 — больше 20 МБ (настраивается через
`MAX_UPLOAD_BYTES`), 422 — не удалось прочитать как изображение, 503 — модель
ещё грузится.

```bash
docker run -d -p 8000:8000 -v "<путь>/ml/weights:/weights:ro" lct7-ml:http
curl -X POST -F "file=@frame.png" http://localhost:8000/detect
```

Проверено 24.09.2026 в контейнере: детекции совпадают с прогоном на хосте,
337 мс на кадр на процессоре, healthcheck отвечает. Модель грузится и
прогревается на старте, поэтому первый запрос не ждёт.
