# CONTRACTS — форматы обмена между частями системы

Договорённости, от которых зависят несколько человек сразу. Меняются только
осознанно: правка формата ломает чужой код.

Три контракта: **детекции** (что выдаёт зрение), **правила** (методика «этап →
техника»), **алерты** (что видит пользователь).

---

## 1. Детекции

Выдаёт `tools/detect_zeroshot.py`, дальше читают: разметка (как черновик),
логика сопоставления, интерфейс.

```json
{
  "meta": {
    "model": "yoloe-26s-seg.pt",
    "params": {"imgsz": 640, "conf": 0.05, "iou": 0.7, "device": "cuda", "verbose": false},
    "created": "2026-09-17T14:30:05",
    "images": 100
  },
  "images": [
    {
      "image": "Screenshot_26.png",
      "width": 1219,
      "height": 809,
      "speed_ms": {"preprocess": 62.3, "inference": 12.0, "postprocess": 18.4},
      "detections": [
        {
          "class_raw": "pile driver",
          "class_ours": "pile_driver",
          "conf": 0.914,
          "bbox": [0.6281, 0.033, 0.7981, 0.6429]
        }
      ]
    }
  ]
}
```

### Правила

| Поле | Договорённость |
|---|---|
| `meta` | всё, что одинаково для прогона: модель, параметры, время, число кадров. В записи кадров не дублируется |
| `bbox` | **доли от размера кадра**, порядок `[x1, y1, x2, y2]`, начало координат — левый верхний угол. Округление до 4 знаков |
| `width`, `height` | пиксели исходного кадра. Без них доли не перевести обратно — нужны для вырезов и отрисовки |
| `conf` | округление до 3 знаков |
| `class_raw` | что ответила модель (промпт). `class_ours` — наш класс из `LABELING_SPEC.md` |
| `detections` | может быть пустым списком. Кадр без находок **остаётся** в файле |
| `speed_ms` | измерение по кадру, в `meta` не выносится |

### Почему доли, а не пиксели

Снимки разного размера (от 1077×807 до 1309×804 у организаторов, до 6000×4000 в
APOCE). Доли не требуют знать размер при сравнении, переносятся между
разрешениями и совпадают с форматом разметки YOLO. Обратный перевод — умножением
на `width` и `height`, которые лежат рядом.

### Поля на будущее

Когда появятся манифест и эталон дат, к записи кадра добавятся:

| Поле | Значения |
|---|---|
| `source_type` | `photo` — фоторепортаж, `cctv` — кадр камеры |
| `date` | ISO-дата съёмки |
| `date_source` | `stamp` — распознан штамп, `manual` — прочитан глазами, `neighbour` — взят по соседям в серии |
| `site_id` | идентификатор площадки |

Логике отклонений нужны именно эти четыре поля: без даты и площадки нельзя
сказать «на объекте X за месяц ничего не изменилось».

## 2. Правила «этап работ → техника»

Артефакт методики. Жюри оценивает его как «явную и проверяемую связь» (ТЗ, 8.3),
поэтому у каждого правила есть ссылка на источник.

```json
{
  "stage_code": "12.3.2",
  "stage_name": "Устройство свай",
  "variants": [
    {
      "name": "буронабивные, CFA",
      "required": [
        {"class": "drilling_rig", "min": 1, "obligation": "normative", "source": "ГЭСН 05-01-079-01"}
      ],
      "auxiliary": [
        {"class": "concrete_pump", "obligation": "normative", "source": "ГЭСН 05-01-079-01"},
        {"class": "concrete_mixer", "obligation": "logical"},
        {"class": "wheel_loader", "obligation": "normative", "source": "ГЭСН 05-01-079-01"}
      ]
    }
  ],
  "unexpected": [{"class": "paver", "note": "гипотеза: покрытие на этапе свай не ведут"}],
  "checkable_by_equipment": true,
  "confidence": "high",
  "version": 1
}
```

| Поле | Смысл |
|---|---|
| `variants` | Нормы допускают **разные комплекты** на один этап: плита делается либо с автобетононасосом, либо башенным краном. Варианты соединяются по «ИЛИ», внутри варианта — по «И» |
| `obligation` | `normative` — машина есть в разделе «Машины и механизмы» расценки ГЭСН; `logical` — обязательна по смыслу, но в норме отсутствует (самосвал, автобетоносмеситель: перевозка и бетон нормируются отдельно). **`logical` не может быть единственным доказательством этапа** |
| `unexpected` | Всегда гипотеза: в нормах таких указаний нет |
| `checkable_by_equipment` | `false` для этапов без крупной техники (гидроизоляция, фасад, озеленение). Система отвечает «не проверяемо по технике», а не «нарушение» |

## 3. Статус этапа — основной вывод решения

Q&A, 18:11 и 36:10: финальный вывод — **отставание либо соответствие графику**,
плюс отчёт о ходе работ с отставанием или опережением. 12:52: прогноз задержки —
«это важно».

Поэтому главный выход системы — не список алертов, а **таблица статусов по всем
этапам графика**. Алерты к ней прилагаются как объяснение.

```json
{
  "site_id": "p08",
  "as_of": "2024-04-24",
  "stages": [
    {
      "stage_code": "12.3.2",
      "stage_name": "Устройство свай",
      "planned": {"start": "2024-01-15", "end": "2024-03-31"},
      "status": "behind",
      "delay_days": 24,
      "evidence_dates": ["2024-02-21", "2024-03-25", "2024-04-24"],
      "basis": "работы наблюдаются после плановой даты окончания",
      "confidence": "medium"
    },
    {
      "stage_code": "12.3.1",
      "stage_name": "Устройство котлована",
      "planned": {"start": "2024-04-01", "end": "2024-06-30"},
      "status": "not_started",
      "delay_days": 23,
      "evidence_dates": ["2024-04-24"],
      "basis": "техника этапа не наблюдается после плановой даты начала",
      "confidence": "medium"
    },
    {
      "stage_code": "12.4.31",
      "stage_name": "Кровля",
      "planned": {"start": "2024-08-01", "end": "2024-09-30"},
      "status": "not_checkable",
      "basis": "этап не определяется по технике (checkable_by_equipment = false)"
    }
  ]
}
```

### Значения `status`

| Значение | Когда |
|---|---|
| `ahead` | работы этапа наблюдаются раньше планового начала |
| `on_track` | наблюдения согласуются с плановым окном |
| `behind` | работы наблюдаются после планового окончания |
| `not_started` | плановое начало прошло, техника этапа не наблюдается |
| `not_observed` | наблюдений в окне нет вообще — нет снимков или низкая наблюдаемость |
| `not_checkable` | этап по технике не проверяется |
| `no_rule` | кода этапа нет в методике — пробел в настройке, не вывод о стройке |

**`delay_days`** — разница в днях между плановой границей и фактическим
наблюдением. Это и есть «прогноз задержки», о котором просили: не модель, а
измеренный сдвиг.

**`delay_days_min` и `delay_days_max`** — тот же сдвиг диапазоном. Нижняя
граница равна `delay_days`. Верхняя — он же плюс типичный промежуток между
наблюдениями (`observation_step_days` в отчёте по площадке): между двумя
съёмками этап мог закончиться в любой день, и **точность оценки не выше частоты
съёмки**. Если второго наблюдения нет, верхняя граница равна `null` — выдумывать
её нельзя, сравнивать не с чем.

Показывать пользователю нужно именно диапазон. Одно число создаёт впечатление
точности, которой у метода нет.

**Различать `not_started` и `not_observed` обязательно.** Первое — утверждение о
стройке, второе — о наших данных. Смешивать их значит выдавать отсутствие снимков
за отсутствие работ.

**`not_checkable` и `no_rule` — тоже разные вещи.** Первое — свойство этапа:
гидроизоляцию по технике не увидишь. Второе — пробел в `configs/rules.json`.
Если их смешать, план с чужой нумерацией этапов целиком станет «не проверяется»,
и система будет молча выглядеть работающей.

## 3a. Поля важности в алерте

Отчёт отдаёт их, потому что интерфейс их отрисовывает, а раньше они не выходили
наружу.

| поле | значения | как получается |
|---|---|---|
| `severity` | `critical`, `attention` | выводится, а не назначается: критично только утверждение о ходе работ при достаточной уверенности и наблюдаемости |
| `severity_reason` | текст | почему важность именно такая |
| `is_hypothesis` | да/нет | истина, когда основание — предположение методики либо низкая уверенность или наблюдаемость |
| `confidence_reason` | текст | на чём держится уверенность |
| `limits_text` | текст | то же, что `cannot_claim`; имя, которого ждёт интерфейс |
| `rule` | `{name, rule_kind, source_ref}` | сработавшее правило: вид обязательности и номер ГЭСН из `configs/rules.json` |

Поле `cannot_claim` остаётся: `limits_text` добавлено рядом, чтобы не ломать
тех, кто уже читает отчёт.

## 3b. Где словарь расходится с интерфейсом — открытый вопрос

`frontend/src/api/schemas.ts` и этот контракт создавались независимо, и наборы
значений разошлись. Здесь это зафиксировано, а не молча подогнано: у наших
различений есть смысл, который нельзя потерять при сведении.

| | отчёт ML | интерфейс |
|---|---|---|
| статусы этапа | `not_checkable`, `no_rule` | `not_checked`, `not_due` |
| типы отклонений | `stage_behind`, `stage_not_started`, `stage_stalled`, `plan_invalid`, `unknown_stages`, `registered_equipment`, `unexpected_equipment` | `stage_mismatch`, `stale_data`, `idle`, `extra_equipment`, `out_of_zone` |

Совпадают только `missing_equipment` и `no_progress`.

Чего нельзя делать при сведении: смешивать `not_started` с `not_observed`
(утверждение о стройке против утверждения о наших данных) и `not_checkable` с
`no_rule` (свойство этапа против пробела в настройке). Остальное обсуждаемо.

## 4. Алерт

Что видит руководитель. По ТЗ (разд. 2) в нём обязательны затронутая зона и
подтверждающие снимки.

```json
{
  "alert_id": "2026-09-17-site3-001",
  "type": "missing_equipment",
  "site_id": "site_3",
  "stage_code": "12.3.1",
  "window": {"from": "2026-08-01", "to": "2026-09-01"},
  "expected": "экскаватор (1+), самосвал (1+)",
  "observed": "экскаватор ×1, самосвалов нет",
  "confidence": "medium",
  "evidence": ["Screenshot_41.png", "Screenshot_42.png"],
  "rules_fired": ["12.3.1/v1"],
  "explanation": "На этапе «Устройство котлована» экскаватор присутствует, самосвалы не наблюдаются на 3 снимках подряд за месяц.",
  "observability": "high",
  "cannot_claim": "Отсутствие самосвалов на снимках не доказывает остановку вывоза грунта: вывоз мог идти вне времени съёмки."
}
```

| Поле | Зачем |
|---|---|
| `type` | из таксономии отклонений: `missing_equipment`, `unexpected_equipment`, `stage_mismatch`, `no_progress`, `stale_data` |
| `confidence` | **ординальный** уровень (`high`/`medium`/`low`), не число. Уверенность детектора не переживает агрегацию по кадрам, окнам и правилам — три честных уровня лучше фальшивых двух знаков после запятой |
| `observability` | насколько зона вообще просматривалась. При `low` система воздерживается от вывода вместо ложного «работы не ведутся» |
| `cannot_claim` | что система **не** вправе утверждать. Это защита от вопроса жюри «а почему вам можно верить» |

## Предлагаемые дополнения v2 (после Q&A) — ТРЕБУЮТ СОГЛАСОВАНИЯ

Не внесено в схемы выше: по правилам ниже формат меняют, договорившись с теми,
кто его читает. Ниже — что Q&A и решения D-007, D-011…D-013 требуют добавить.

**1. Снимок: источник даты и площадки.**

| Поле | Значение |
|---|---|
| `date_source` | `channel` / `exif` / `ocr` / `neighbour` / `manual` — откуда взята дата. Метаданные **не гарантируются** (08:22), поэтому источник обязан быть явным: интерфейс показывает, что пришло от камеры, а что выведено |
| `site_source` | `channel` / `manual`. Автоматическое восстановление площадки закрыто (D-013) |

**2. Единица сопоставления — тур, а не кадр.** Один объект в одну дату — это
несколько кадров с разных точек. Состав техники тура = объединение по кадрам,
количество = **максимум** по кадрам, не сумма: одна машина, снятая с пяти точек,
остаётся одной машиной. Без этого техника, попавшая в один ракурс из пяти,
станет «отсутствующей» и породит ложные алерты.

**3. Правило: ссылка на укрупнённый этап.** Добавить `observable_stage` —
наблюдаемый этап из D-011. Само сопоставление «код работы → наблюдаемый этап»
живёт отдельной версионируемой таблицей, справочник не переписывается.

**4. Техника: работа или простой.** Обязательное требование (11:58). Признак
уровня тура, не кадра: `activity: working / idle / unknown`. Источник вывода —
изменение сцены между соседними турами и положение машины относительно рабочей
зоны. Распознавание действия по одному кадру не делаем: формат входа — только
отдельные изображения (07:37).

**5. Алерт: прогноз.** Заявлен как важный (12:52). Поля: ожидаемое отставание в
днях и на чём основано (темп по предыдущим турам против плановой длительности).
Прогноз без указания основания в алерт не выводить.

**6. Новый тип отклонения** к таксономии `type`: `equipment_idle` — техника
присутствует, но простаивает. И `out_of_zone` — машина вне своей рабочей зоны
(20:29), как гипотеза, а не как нарушение.

## 5. Как менять контракт

1. Обсудить с теми, кто читает формат.
2. Поднять версию в `meta` либо в поле `version` правила.
3. Записать изменение в `DECISIONS.md`, если оно ломает совместимость.
