# Ассистент по отчёту: как встроить в интерфейс

Документ для тех, кто будет переносить ассистента из ML-сервиса в продукт.
Отвечает на три вопроса: что ручка делает, чего она намеренно не делает и какие
требования к интерфейсу из этого следуют.

Сейчас ассистент живёт только в ML-сервисе: ручка `POST /ask` и CLI
`tools/ask_report.py`. В `frontend/` и `backend/` его нет.

---

## 1. Что это

Пользователь спрашивает по-русски: «где отставание и на сколько», «что с p03».
Ассистент отвечает пересказом **готового отчёта**, со ссылкой на площадку и код
этапа.

Модель не считает и не решает. Все статусы, сдвиги в днях и отклонения
порождаются правилами в `tools/match_schedule.py` **до** того, как ассистент
что-либо увидит. Он получает готовый JSON и перекладывает его в человеческую
фразу.

Это граница из решения D-020, и она не про осторожность. Отчёт уходит в
департамент; каждое число в нём должно прослеживаться до нормы ГЭСН и до
снимка-доказательства. Число, которое придумала языковая модель,
проследить нельзя — поэтому она и не допущена в порождение выводов.

**Ассистент — удобство чтения, а не источник данных.** Источник истины всегда
отчёт.

## 2. Контракт ручки

### Запрос

```
POST /ask
Content-Type: application/json
```

```json
{
  "question": "где отставание и на сколько",
  "report": { "...": "отчёт целиком, как его вернул POST /report" },
  "site_id": "p03"
}
```

| поле | тип | обязательно | описание |
|---|---|---|---|
| `question` | string | да | от 3 до 500 символов |
| `report` | object | да | **отчёт целиком**, как его вернул `POST /report` |
| `site_id` | string | нет | ограничить одной площадкой |

**Ручка не хранит состояние.** Она не помнит отчётов и не ходит за ними сама:
отчёт приходит в теле запроса. Значит, отчёт держит бэкенд и присылает его с
каждым вопросом. Диалога тоже нет — каждый вопрос независим, предыдущие ответы
в контекст не попадают. Если нужен диалог, его придётся собирать на стороне
бэкенда, и тогда проверку чисел надо будет применять к каждому ответу
отдельно.

Отчёт по десятку площадок — это сотни килобайт JSON. Сервис сам урезает его
перед отправкой в модель (`ask_report.compact`: выбрасывает служебные поля,
оставляет по паре кадров-доказательств), но по сети едет полный. Учитывайте при
выборе таймаутов и лимитов тела запроса.

### Ответ

```json
{
  "answer": "На площадке p03 этап 12.3.2 «Устройство свай» отстаёт на 14–43 дня...",
  "verified": true,
  "numbers_not_in_report": [],
  "numbers_of_other_site": [],
  "limits": "Проверяются числа, а не смысл: верное число может быть отнесено не к тому этапу, и проверка этого не увидит. Источник истины — сам отчёт, ответ лишь пересказывает его."
}
```

| поле | тип | описание |
|---|---|---|
| `answer` | string | текст ответа |
| `verified` | bool | прошёл ли ответ обе проверки чисел |
| `numbers_not_in_report` | string[] | числа из ответа, которых в отчёте нет вовсе |
| `numbers_of_other_site` | string[] | числа вида `p03: 114` — есть в отчёте, но по другой площадке |
| `limits` | string | чего проверка не умеет; **показывать вместе с ответом** |

### Ошибки

| код | когда | что делать |
|---|---|---|
| 422 | `question` короче 3 или длиннее 500 символов (валидация; `detail` — список ошибок) | валидировать на фронте заранее |
| 422 | вопрос или ответ вне темы отчёта (scope guard; `detail` — объект с полями `code` и `message`) | показать `message` из `detail`, не повторять |
| 400 | в отчёте нет площадки из `site_id` | не повторять, показать «нет такой площадки» |
| 503 | не заданы `LLM_BASE_URL`, `LLM_API_KEY` или `LLM_MODEL` | не повторять; скрыть ассистента в интерфейсе |
| 504 | внешняя модель не ответила за 120 с | предложить повторить |

503 — не сбой, а штатное состояние стенда без доступа к модели. Интерфейс
должен из него выходить осмысленно: не показывать сломанную кнопку, а не
показывать ассистента вовсе.

## 3. Как устроена проверка чисел

Понимать это нужно, чтобы правильно показывать результат.

Обычный способ бороться с выдумками — уговор в запросе: «отвечай только по
данным». Уговор нельзя проверить. Мы проверяем по факту.

Перед отправкой из отчёта собирается множество всех чисел. После ответа из него
извлекаются все числа и сверяются с этим множеством. Два уровня:

1. **Число, которого в отчёте нет вовсе** → `numbers_not_in_report`.
2. **Число есть, но по другой площадке** → `numbers_of_other_site`. Ответ
   режется по упоминаниям `p03`, `p08` и так далее; всё, что сказано после
   метки и до следующей, считается сказанным про эту площадку.

Две детали, из-за которых проверка не разваливается на настоящих данных:

- разряды склеиваются: «4 500 000» проверяется целиком, а не тремя кусками,
  каждый из которых нашёлся бы в отчёте по отдельности;
- даты раскладываются на части, потому что модель законно напишет «31 марта
  2024», а в отчёте лежит `2024-03-31`.

**Чего проверка не умеет** (это и есть содержимое `limits`):

- она сверяет числа, а не смысл. Верное число, отнесённое не к тому этапу,
  пройдёт;
- выдуманное число, случайно совпавшее с другим числом отчёта, пройдёт.

Поэтому проверка — сито, а не доказательство. Список исключений намеренно не
заводится: «общеупотребительные» числа вроде 10 или 100 — ровно тот случай, где
выдумка и прячется.

## 4. Требования к интерфейсу

Они не косметические. Проверка чисел имеет смысл только если её результат виден
пользователю.

**1. `verified: false` нельзя показывать как обычный ответ.** Нужна явная
пометка, что ответ не прошёл проверку, и перечень чисел из
`numbers_not_in_report` и `numbers_of_other_site`. Формулировка вроде «сверьтесь
с отчётом: эти числа в нём не найдены».

**2. `limits` показывать рядом с ответом, а не в подсказке по наведению.** По
замыслу оговорка едет вместе с числом и не теряется по дороге — так же, как в
самом отчёте оговорка лежит рядом со сдвигом сроков, а не в сноске.

**3. Ответ не является документом.** Не сохранять его как поле объекта, не
класть в выгрузки CSV/XLSX/PDF, не подставлять в печатные формы. Туда идёт
отчёт. Ответ ассистента — временный текст на экране.

**4. Дать дорогу к источнику.** Ассистент обязан называть площадку и код этапа;
интерфейс должен уметь по ним перейти на соответствующий этап в отчёте. Без
этого проверяемость, ради которой всё сделано, не работает. **При ошибке 422
`out_of_scope` показать пользователю значение `message` из `detail`, не повторять
запрос.**

**5. Ждать придётся.** Таймаут до внешней модели — 120 с, обычный ответ
заметно быстрее, но мгновенным не будет. Нужен индикатор ожидания и защита от
повторного нажатия: каждый вопрос — платный вызов.

**6. Не давать ассистенту менять данные.** Он только читает. Никаких «применить
предложение» или «обновить план по ответу».

## 5. Настройка

Три переменные, читаются из окружения процесса, а при их отсутствии — из
`ml/.env` (файл в git не попадает):

```
LLM_BASE_URL=https://.../v1
LLM_API_KEY=...
LLM_MODEL=...
```

Сервис обращается к `{LLM_BASE_URL}/chat/completions` — формат OpenAI, заголовок
`Authorization: Bearer {LLM_API_KEY}`, `temperature: 0`. Подойдёт и облачный
сервис, и локальная модель, которая держит этот формат.

**Ключ не должен попадать на фронтенд.** Вызов идёт только по цепочке
браузер → бэкенд → ML-сервис. Ручка `/ask` не должна торчать наружу без
аутентификации: каждый вызов тратит деньги.

**В Docker** переменные приходят из корневого `.env`; контейнер `ml` получает их
через `environment`, `backend` видит их пусто (раздел «Ассистент по отчёту (LLM)»
в `deploy/README.md`, см. также `deploy/docker/common/core.yaml`).

**Доступность ассистента.** Запрос `GET /meta` возвращает поле `"assistant": true` если
все три переменные установлены, иначе `false`. При запросе к только что
запущенному сервису `/meta` может ответить 503 пока модель прогревается (до 90 с).

Проверить, что модель доступна и какие имена моделей она отдаёт:

```bash
python tools/suggest_stage_mapping.py --list-models
```

## 6. Куда встраивать

По соглашениям репозитория (`docs/architecture.md` §6) внешние системы живут в
`backend/app/adapters/`. Ассистент — такая же внешняя система, как ML-сервис
детекции.

**Как это устроено в продукте:**

**Ручки:**
- `POST /api/sites/{site_id}/assistant/ask` — задать вопрос по отчёту, тело:
  `{"question": "..."}` (3–500 символов после strip);
- `GET /api/assistant/status` — получить статус доступности (`{"enabled": bool}`).

**Ответ на `/ask`:**
```json
{
  "answer": "текст ответа",
  "verified": true,
  "numbers_not_in_report": [],
  "numbers_of_other_site": [],
  "limits": "ограничения проверки",
  "site_label": "p1",
  "stages": [{"ref": "этап 1", "stage_id": "<uuid>"}]
}
```

**Ошибки:**

| статус | код | когда |
|---|---|---|
| 404 | – | площадка не найдена, не принадлежит пользователю, график не загружен |
| 422 | – | вопрос короче 3 или длиннее 500 символов (валидация, `detail` — список) |
| 422 | `out_of_scope` | вопрос или ответ вне темы отчёта |
| 429 | `rate_limited` | превышен лимит частоты (по умолчанию 10 в минуту) |
| 413 | `report_too_large` | отчёт больше макс. размера |
| 503 | `assistant_unavailable` | ML не настроен, недоступен или вернул 503 |
| 504 | `assistant_timeout` | ML не ответил или вернул 504 |
| 400 | `assistant_bad_request` | ML вернул 4xx ошибку |

**Без аутентификации.** Проект не имеет реальной аутентификации; rate limit (10/мин
по умолчанию через `ASSISTANT__RATE_LIMIT_PER_MIN`) — единственный механизм защиты.
ML-сервис не опубликован за пределы compose-сети.

Кеш-ключ ответа завязывать на площадку и отчёт, а не только на текст вопроса:
тот же вопрос по обновлённому отчёту — другой ответ.

## 7. Как проверить, что работает

Сервис поднят по инструкции из `INTEGRATION.md` §2.

```bash
# 1. получить отчёт
curl -X POST http://localhost:8000/report \
     -H "Content-Type: application/json" \
     -d @request.json > report.json

# 2. спросить по нему
python - <<'PY'
import json, urllib.request
report = json.load(open("report.json", encoding="utf-8"))
body = json.dumps({"question": "где отставание и на сколько",
                   "report": report}, ensure_ascii=False).encode()
r = urllib.request.Request("http://localhost:8000/ask", data=body,
                           headers={"Content-Type": "application/json"})
print(json.dumps(json.load(urllib.request.urlopen(r)),
                 ensure_ascii=False, indent=2))
PY
```

То же самое из командной строки, без сервиса:

```bash
python tools/ask_report.py "где отставание и на сколько"
python tools/ask_report.py "что с p03" --site p03
python tools/ask_report.py "..." --dry-run    # показать запрос и выйти
```

`--dry-run` работает и без доступа к модели: печатает, сколько площадок попало в
запрос, сколько чисел собрано для сверки и как выглядит сам запрос. Удобно,
чтобы понять размер тела, не тратя вызов.

Сценарий, который стоит прогнать руками перед сдачей: задать вопрос про
площадку, которой в отчёте нет, и убедиться, что интерфейс показывает ответ как
непроверенный, а не как факт.

## 8. Вторая поверхность: разбор названий работ

Для полноты картины — этим языковая модель занимается кроме ассистента.

`tools/suggest_stage_mapping.py` сопоставляет произвольные названия работ из
плана заказчика с кодами этапов. В плане 374 строки; регулярные выражения
распознали ноль. Модель с добавленными границами этапов и вторым проходом
самопроверки даёт точность 0.93 (было 0.77 без них) — замер E27, эталон в
`data/reference/mapping_review.csv`.

**Это офлайн-инструмент, а не ручка.** Он запускается один раз при заведении
нового плана, его предложения просматривает человек, результат ложится в
`configs/stage_mapping.json`. Встраивать в интерфейс сейчас не требуется. Если
когда-нибудь потребуется, действует то же правило: предложение модели —
черновик, который подтверждает пользователь, а не запись в данные.
