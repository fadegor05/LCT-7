## 1. Почему сейчас, а не перед сдачей

Скрытого теста не будет — на Q&A это прозвучало трижды (13:30, 31:54, 33:22).
Оценка экспертная, **на примерах, которые готовим мы сами** (32:05, 33:40), и
отдельно сказано, что смотрят на **разнообразие подборки**: сезонность,
количество техники, этапы, типы объектов. Решение зафиксировано в `DECISIONS.md`
D-008.

Отсюда: состав набора влияет на балл так же прямо, как код. Четыре причины не
откладывать.

1. **Это единственная линейка прогресса.** `alert agreement 5/7` из B0-oracle
   посчитан на 21 кадре и двух площадках. Каждое улучшение детектора надо
   пересчитывать на **фиксированном** наборе, иначе не отличить «модель стала
   лучше» от «примеры стали проще». Заморозить набор нужно раньше модели.
2. **Он определяет, что размечать дальше.** Размечен 21 кадр из 100. Какие из
   оставшихся брать — ответ даёт только состав набора. Без него разметка идёт
   наугад.
3. **Он вскрывает дыры, пока их можно закрыть.** В Kaggle бульдозеров **0**,
   катков **4**, лета нет вообще (A1). Если это выяснится 27.09 — сделать уже
   ничего нельзя; если 19.09 — можно добрать внешние данные (разрешено до 5
   ссылок на открытые источники, 07:56) или честно сузить заявку.
4. **Кейс — это не картинка.** Это тройка **(площадка, дата, строка графика)**.
   Дата есть на 68 кадрах из 100, распознаётся 62. `site_id` проставляется
   руками — E7 доказал, что по пикселям площадки не группируются. График
   синтезируем сами (разрешено, 24:48). Эта сборка ручная и в конце не ужимается.

**Кто делает.** Это **не** задача ML-инженера: подбор кадров, простановка
`site_id` и даты, строка графика и ожидаемый вердикт — работа аналитика.
ML только прогоняет цепочку поверх готового набора. Поэтому работа **не
блокируется моделью** и начинается сегодня.

## 2. Что считается одним кейсом

Один кейс = один показ на защите. Минимальный комплект:

| Поле | Откуда берётся |
|---|---|
| `case_id` | наш |
| `site_id` | `data/reference/sites.csv`, колонка `site_id` |
| `dates` | штамп (`read_date_stamp.py`) или руками; источник помечать |
| `frames` | имена файлов из выданных 100 снимков |
| `stage_code` | код из `configs/rules.json` (14 этапов) |
| `expected_verdict` | что система **должна** ответить — пишется до прогона |
| `proves` | ради какого свойства кейс в наборе |
| `status` | `draft` / `frames_ok` / `schedule_ok` / `verified` |

**Правило:** `expected_verdict` пишется **до** прогона цепочки. Иначе набор
подстраивается под поведение системы и перестаёт быть проверкой.

Строка графика под кейс добавляется в `data/reference/schedule_demo.csv` и явно
помечается как демо-данные — этого требует раздел «условия и ограничения»
документации.

## 4. Оси разнообразия

Закрывать осознанно, по каждой оси отмечать покрытие:

- **сезон** — зима / весна / лето / осень (лето — дыра: его нет в обучении);
- **время суток и погода** — снег, контровой свет, сумерки;
- **плотность** — 1 машина в кадре против 10 и больше;
- **этап** — минимум 6 разных `stage_code` из 14;
- **тип объекта** — жильё / образование / здравоохранение (по справочнику);
- **ракурс** — с земли, с соседнего здания, с дрона.

## 7. Как проверяется кейс

```
tools/site_state.py     → состояние площадки на дату
tools/match_schedule.py → статус этапа и алерт
```

Прогон делается **дважды**: на предсказаниях детектора и на ручной разметке
(`tools/labels_to_detections.py`). Совпадение статусов — метрика
**alert agreement**, сейчас 5/7. Её пересчёт после каждого улучшения детектора и
есть измерение прогресса.

Кейс считается `verified`, когда прогон на эталоне даёт ровно
`expected_verdict`. Расхождение — это либо ошибка правил, либо неверно записанное
ожидание; разбирать до заморозки.
