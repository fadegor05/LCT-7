## D-001. Лицензия репозитория: AGPL-3.0 — ПРИНЯТО 2026-09-18

**Решение.** Весь репозиторий (backend, frontend, ml) — под AGPL-3.0, файл
`LICENSE` в корне (PR #4). Текст дословный с gnu.org.

**Почему.** По ТЗ (разд. 7.2) код сдаётся открытым, а без `LICENSE` он формально
«все права защищены». Всё семейство Ultralytics (YOLO26, YOLOE), которое мы
используем, — AGPL-3.0, и по позиции разработчика это распространяется на
обученные веса. Значит AGPL на нас распространяется и так.

**Альтернатива.** Apache-стек (RF-DETR S/M, D-FINE, DEIM, MM-Grounding-DINO) —
чище для внедрения у заказчика, но закрывает дорогу к Ultralytics. Выбор
обратим только в одну сторону: код под Apache можно взять в AGPL-проект, наоборот
нельзя. Поэтому AGPL сейчас, выбор детектора — на G1.

**Что это значит для команды.** Зависимости backend и frontend (FastAPI, React,
SQLAlchemy, Vite — MIT; Granian — BSD; Dishka — Apache-2.0) с AGPLv3 совместимы.
Обязанность одна: тот, кто разворачивает сервис, даёт его пользователям доступ к
исходному коду (§13). Для открытого репозитория это выполняется само.

**Что сделает решение неверным:** если заказчик потребует закрытого внедрения
без покупки Enterprise-лицензии Ultralytics — тогда детектор меняется на
Apache-стек, и лицензию репозитория можно пересмотреть.

## D-002. Окружение: venv + CUDA-сборка torch — ПРИНЯТО 2026-09-16

**Решение.** `.venv` в корне проекта, Python 3.12, запуск без активации через
`.venv\Scripts\python.exe`. Torch ставится **не с PyPI**, а с индекса PyTorch.
Зафиксировано: `torch==2.14.0+cu130`, `torchvision==0.29.0+cu130`,
`ultralytics==8.4.153`. Проверено на RTX 4060 Laptop (sm_89), драйвер 610.74.

**Почему.** Обычный `pip install torch` ставит сборку `+cpu`, и GPU молча не
используется. Порядок установки тоже важен: сначала `ultralytics`, потом torch —
иначе ultralytics подтягивает CPU-сборку как зависимость и перетирает CUDA-версию.

**Побочное.** На Windows пришлось выключить Smart App Control: он блокировал
неподписанные DLL из колёс pip (`WinError 4551` на `c10.dll`). Альтернатива без
изменения системы — работа в WSL2. Выключение SAC необратимо без переустановки
Windows — учтено и принято сознательно.

## D-003. Таксономия шире списка ТЗ — ПРИНЯТО 2026-09-16

**Решение.** Размечаем 24 класса вместо 8 из ТЗ: добавлены буровая установка,
башенный и гусеничный краны, копёр, установка «стена в грунте», автобетононасос,
экскаватор-погрузчик, асфальтоукладчик и другие. Иерархия coarse → fine, при
неуверенности ставится coarse-класс.

**Почему.** На выданных снимках чаще всего встречаются именно буровые установки и
башенные краны, которых в списке ТЗ нет, и именно они дают однозначный сигнал
этапа работ (`research/part_I`, вывод 5). ТЗ (разд. 6.2) расширение прямо
разрешает.

**Что сделает решение неверным:** если на сверке по §6 `LABELING_SPEC.md`
окажется, что размечающие не различают пару классов стабильно — эта пара
схлопывается в coarse.

## D-004. Валидация по двум доменам, сплит по площадкам и камерам — ПРИНЯТО

**Решение.**
- Фото организаторов: grouped K-fold **по площадкам**, hold-out — новые снимки
  других объектов из открытых источников.
- Kaggle CCTV: **leave-camera-out** по прореженным кадрам, 2–3 камеры целиком в
  hold-out.
- В отчёте всегда матрица «обучение на домене X → тест на домене Y» и срезы по
  сезону, ракурсу, размеру объекта.

**Почему.** Снимки идут сериями одной площадки, в одну дату их бывает несколько.
Случайный сплит по кадрам даст утечку и завышенную оценку. У Kaggle то же самое
по камерам: родной `train`/`valid` до проверки пересечения камер использовать
нельзя.

## D-005. Данные на A100 возим через HuggingFace — ПРИНЯТО

**Решение.** Приватный dataset-репозиторий на HF; на сервере задача тянет данные
напрямую. `culab push` используется только для кода.

**Почему.** У `jupyter.culab.ru` эфемерный диск (данные пропадают при
перезагрузке пода), а фильтр `culab push` исключает `*.csv`, архивы и веса.
Побочная выгода: у HF есть ревизии, и в документации можно сослаться на точную
версию данных — это работает на критерий воспроизводимости.

**Ограничение.** Снимки организаторов и всё производное — только в приватном
репозитории.

## D-006. 100 снимков организаторов — только оценочная выборка — ИЗМЕНЕНО D-014 (2026-09-20)

**Решение.** Кадры организаторов **не используются для обучения**. Обучение идёт
на Kaggle CCTV (сплит по камерам) и APOCE; эти 100 снимков — фиксированная
оценочная выборка для проверки переноса на домен фоторепортажей.

**Почему.** Исходно разметка `site_id` требовалась, чтобы не допустить утечки
между обучением и валидацией. Но разделить эти снимки по площадкам оказалось
дорого: за 2.5 года съёмки одна площадка меняется до неузнаваемости, а разные
московские стройки похожи между собой. Проверены три подхода:
- глобальные признаки ImageNet (resnet18) — склеили всё в 7 групп, бесполезно;
- ORB + гомография — склеил 31 кадр с датами от 2023 до 2026: повторяющиеся
  текстуры заборов и труб дают согласованные преобразования;
- ручной просмотр в полном размере — работает, но 100 кадров это часы, и часть
  пар остаётся спорной даже после сравнения горизонтов.

Если эти кадры никогда не попадают в обучение, **утечка внутри них невозможна**,
и точная разметка площадок перестаёт быть обязательной.

**Где `site_id` всё же нужен:** для демонстрации отклонений во времени и для
срезов в отчёте. Достаточно нескольких уверенно опознанных серий, они размечены
в `data/interim/sites.csv` (59 кадров, 11 площадок, колонка `confidence`).

**Что сделает решение неверным.** Если выяснится, что 100 кадров слишком мало
для оценки (например, редкие классы встречаются 2–3 раза), придётся добирать
обучающие данные из этого же домена — тогда разметка площадок снова станет
обязательной.

## D-007. «Работает / простаивает» — обязательная функция — ПРИНЯТО 2026-09-17, ИСПРАВЛЕНО 2026-09-20

**Основание.** Q&A, 11:58: определять, работает техника или простаивает,
**обязательно** — «иначе не получится». Плюс 20:29: их собственный пример
аномалии — «экскаватор просто стоит у въезда на площадку, но никак не задействован
в процессе производимого этапа».

**Что меняется.** Раньше мы сознательно исключали распознавание активности
(`docs/ML_ACTION_PLAN.md`, §0, «не делать»): на одиночных фотографиях движение не
наблюдаемо. Теперь это требование заказчика, и исключить его нельзя.

**Подход.** Движение недоступно, поэтому судим по контексту кадра:
- **положение рабочего органа** — ковш в грунте или поднят, стрела развёрнута к забою;
- **следы работы рядом** — свежий отвал, нарушенный грунт, пыль;
- **парная техника** — самосвал под погрузкой у экскаватора, миксер у бетононасоса;
- **зона** — машина в рабочей зоне или на стоянке у въезда и вдоль забора;
- **люди рядом** в рабочих позах.

Ни один признак по отдельности не доказателен, поэтому выдаём **три состояния**:
`working` / `idle` / `unknown`, и `unknown` — нормальный ответ. Обещать точное
определение по одному кадру нельзя, и на защите это честнее любых процентов.

**Что сделает решение неверным:** если на разметке окажется, что признаки не
различают состояния лучше случайного — оставляем только `zone`-признак (техника
вне рабочей зоны) и говорим об этом прямо.

### Правка 2026-09-20: два признака сняты, один поднят, формулировка сужена

Основание — E11a (разбор уже имевшейся разметки активности) и `research/part_N_activity.md`.

**Что измерено.** Человек, глядя на полноразмерный кадр без ограничения по
времени, выносит суждение об активности **в 22% случаев** (37 `working`, 27
`idle`, 233 `unknown` на 297 рамках). На **62 крана** — 29 башенных и 33
гусеничных — вынесено **ровно одно** непустое суждение. У крана нет наблюдаемого
на статике рабочего органа: стрела выглядит одинаково при работе и простое.
Это потолок для любой модели, обучаемой на такой разметке, а не оценка модели.

**Что говорит литература.** Ни одна работа 2007–2026 гг. не определяет
working/idle строительной техники **по одному кадру**; все без исключения строят
признак из разности между кадрами. Даже по полноценному видео лучший найденный
честный результат бинарной задачи — F1 76%.

**Правка списка признаков:**

| Признак | Было | Стало | Почему |
|---|---|---|---|
| **парная техника** | один из пяти | **опорный** | Единственный количественно подтверждённый: в разобранном кейсе **74% всего времени простоя** экскаватора приходится на «рядом нет ни одного самосвала». Правило группировки считается по одному кадру поверх нашего детектора бесплатно |
| положение рабочего органа | один из пяти | вспомогательный | Поза оценивается точно (AP 96.5%), но единственное опубликованное правило «поза → состояние» требует проверки неподвижности корпуса **между кадрами** |
| зона | один из пяти | вспомогательный | Требует стройгенплана либо ручной разметки зоны; на сменном ракурсе между кадрами не переносится (E7) |
| следы работы рядом | один из пяти | **снят** | Относится к состоянию площадки, а не к активности машины. Переезжает в признаки стадии, `research/part_M_scene_stage.md` |
| **люди рядом** | один из пяти | **снят** | Не подтверждён ничем, а единственное найденное фактическое наблюдение указывает в **обратную сторону**: люди рядом с экскаватором сопровождали простой, а не работу |

**Формулировка, которую произносим.** Не «определяем, работает техника или
простаивает», а **«определяем для техники с наблюдаемым рабочим органом —
экскаватор, буровая; для башенных и гусеничных кранов честно отвечаем
„неизвестно“, потому что по одному кадру этого не видит и человек»**. Три
состояния и нормальность `unknown` остаются в силе.

**Открыто.** `part_N` предлагает заменить величину на **вовлечённость в этап**
(`engaged` / `not_engaged` / `unknown`) — заказчик сам описал аномалию не через
движение, а через «никак не задействован в процессе производимого этапа» (20:29).
Переименование выхода делать **только после** замера согласия двух разметчиков,
а не до: если согласие низкое, честнее оставить `unknown` ответом по умолчанию.

**Ловушка до любого обучения.** 64% всех суждений (41 из 64) приходятся на одну
группу `p08 2024-04-24`. Обучение или валидация активности на этой разметке
измерит узнавание одной сцены. Разметку добирать вширь по площадкам.

## D-008. Демонстрационный набор — это и есть тестовая выборка — ПРИНЯТО

**Основание.** Q&A, 13:30 / 31:54 / 33:22: скрытого теста и проверочного датасета
не будет, прозвучало трижды. 32:05 и 33:40: оценивать будут **подобранные нами
примеры** «на предмет их разнообразия, возможно, учёта сезонности, количества
техники, строительных этапов и объектов».

**Следствие.** Состав демо-набора влияет на оценку напрямую, наравне с кодом.
Собираем осознанно: разные сезоны, погода, время суток, число машин на кадре,
разные этапы и типы объектов, плюс заведомо трудные случаи (аэросъёмка, мелкая
техника, ночь) — чтобы показать и границы применимости.

**Побочно:** это усиливает D-006. Выданные 100 снимков остаются оценочной
выборкой, и разметка площадок для сплита по-прежнему не нужна.

## D-010. Формат календарного плана на входе — ПРИНЯТО (с оговоркой)

**Основание.** Q&A, 09:41: выдан справочник этапов без дат. 41:49: «на вход будет
подаваться эксэлевский файл, в котором перечислены аналогичные этапы работ, только
с привязкой к конкретным датам». 42:32: техники в этом файле не будет — её
определяем мы и даём вводить пользователю.

**Решение.** Парсер принимает Excel той же структуры, что выданный справочник,
плюс колонки дат начала и окончания. Даты для демо синтезируем сами (это Q&A
разрешает, 24:48).

**Оговорка снята 24.09.2026.** Получены два реальных плана со строек, и оба
разбираются `tools/parse_schedule.py`:

| формат | что внутри | особенности |
|---|---|---|
| Excel, 67 строк | иерархия 1 / 1.1 / 2 / 2.1, название, начало, окончание | даты числами Excel; **13 строк с «30.02.2027»** — такого дня нет |
| PDF из MS Project, 112 задач | те же поля, даты с днём недели («Пн 07.06.19») | двузначный год; один этап разбит на секции и этажи |

Три вывода, которые заранее не предполагались:
1. **Даты бывают некорректными.** Парсер помечает строку и продолжает, а не
   падает: в выданном файле таких строк 13 из 67.
2. **Один наш этап встречается несколько раз** — каркас отдельной строкой на
   каждую секцию. Сводим к минимальному началу и максимальному окончанию.
3. **Большая часть работ нам не соответствует** (внутренняя отделка,
   оборудование, сдача в надзор): 50 строк из 67 и 90 задач из 112. Они в
   график не попадают — по технике не проверяются, и молчать честнее, чем
   выдумывать вердикт.

## D-011. Укрупнение этапов — по наблюдаемости, не по структуре справочника — ПРИНЯТО 2026-09-17

**Решение.** Работы справочника сводятся в **8 наблюдаемых этапов** плюс один
блок «вне наблюдения». Критерий слияния ровно один: две работы идут в один этап,
если камера не может их различить. Сопоставление живёт отдельной таблицей
«код работы → наблюдаемый этап» (многие-к-одному), версионируется рядом с
`ruleset`, справочник и парсер не трогаются.

| Наблюдаемый этап | Коды | Маркеры техники |
|---|---|---|
| Подготовка площадки | `10.*` | бульдозер, экскаватор, самосвал, автокран |
| Котлован и земляные работы | `12.3.1`, `12.3.3`, `12.3.7` | экскаватор, самосвал |
| Сваи и ограждение котлована | `12.3.2`, `12.3.5`, `12.3.6` | буровая установка, гусеничный кран |
| Фундамент и подземная часть | `12.3.4`, `12.3.9`–`12.3.11` | автобетононасос, бетоносмеситель |
| Каркас надземной части | `12.4.4`, `12.4.5`, `12.4.8`–`12.4.10`, `12.4.28`–`12.4.30` | башенный кран, бетононасос |
| Кровля и фасад | `12.4.11`, `12.4.31`, `12.4.32`, `12.4.37`–`12.4.57`, `12.6.1` | автовышка, подъёмник, автокран |
| Наружные сети | `12.5.1` | экскаватор, трубоукладчик |
| Благоустройство | `12.7.*`, `12.4.12`, `12.4.14` | каток, асфальтоукладчик, самосвал |
| **Вне наблюдения** | `12.5.2`, `12.6.2`–`12.6.13`, `12.4.33`–`12.4.36` | маркеров нет |

Дорожно-тоннельная ветка (`12.1`, `12.2`, `12.3.8`, `12.4.13`–`12.4.27`) —
отдельный профиль под тип объекта «Дороги», в демо не берётся.

**Почему.** Укрупнять разрешено прямо (`QA_SESSION` 17:28), как и ограничиться
внешней аналитикой (32:19); ментор советовал качественно по ограниченному числу
разделов, а не широко и поверхностно (34:11). Различие, которого не видно на
кадре, не даёт пользы, но порождает ложные отклонения.

**Расхождение, требующее уточнения.** В Q&A звучит «работы сгруппированы по 4
этапам» и «4 уровня детализации», а в выданном файле — 2 раздела верхнего уровня
(10 и 12), 21 подраздел и **5 уровней** вложенности. Цифра «4» ни на что в файле
буквально не ложится. Вопрос задать в чате задачи.

**Что сделает решение неверным:** если на вход подадут график, детализированный
до уровня, где наши укрупнённые этапы перестают быть подмножествами его строк.
Защита — сопоставление таблицей, а не переписыванием справочника.

**⚠ Решение записано, но не реализовано (обнаружено 2026-09-20).** Таблица выше
сводит `12.3.4` и `12.3.9`–`12.3.11` в один наблюдаемый этап «Фундамент и
подземная часть», а `configs/rules.json` держит их **отдельными правилами**: 14
правил на уровне кодов работ, а не 8 наблюдаемых этапов. То есть онтология
существует на бумаге, а пайплайн работает на более дробном уровне, где этапы
заведомо неразличимы (E5). Приведение в соответствие — D-015.

## D-012. Ненаблюдаемые работы дают предупреждение, а не вердикт — ПРИНЯТО 2026-09-17

**Решение.** Для блока «вне наблюдения» (внутренняя отделка, двери, электрика,
внутренние сети) система не выносит суждения о соответствии графику, а выдаёт
явное «работы вне зоны контроля ИИ, требуется дополнительная проверка».
То же поведение — когда часть площадки не попала в кадр.

**Почему.** Ровно об этом просили на 13:01: не анализировать молча, а выводить
предупреждение. Плюс в контракте правил уже заложено `checkable_by_equipment:
false`. Ограничение превращается в заявленную заказчиком функцию, а не в дыру.

**Что сделает решение неверным:** ничего в пределах этого хакатона. Риск
обратный — соблазн тихо пропустить эти работы и получить вопрос жюри «а почему
по отделке всегда всё хорошо».

## D-013. Кластеризация площадок по пикселям — ЗАКРЫТО 2026-09-17

**Решение.** `site_id` проставляется вручную в манифесте; в интерфейсе —
привязка пачкой. Автоматическое восстановление площадки из изображения не
делаем.

**Почему.** E7: на 862 парах SIFT + RANSAC не разделяет `same_date`, `same_site`
и `diff_site` — медиана 4 инлаера везде. Контроль пайплайна пройден (кадр сам с
собой 900/900). У снимков нет визуального перекрытия даже внутри одного выезда.
Способ привязки отдан команде явно (08:50), и простое решение здесь надёжнее.

**Важно для позиционирования:** это свойство выданной подборки, а не задачи. В
эксплуатации камера стационарна, `camera_id` даёт группировку бесплатно.

## D-014. Часть снимков организаторов идёт в обучение — ПРИНЯТО 2026-09-20

**Решение.** D-006 («100 снимков организаторов — только оценочная выборка»)
смягчается. Площадки **p05, p07, p09, p11** (24 кадра, 151 рамка) идут в
обучение. Площадки **p03 и p08** (21 кадр, 146 рамок) остаются оценочными и в
обучение не попадают никогда. Неразмеченные кадры без площадки — тоже не
обучающие.

**Почему.** E9 показал, что дообученные модели Захара не выдают ни одного
специфичного класса (`drilling_rig`, `pile_driver`, `dwall_rig`, `paver`,
`grader`, `concrete_pump`, `roller`), а только они подтверждают этап работ.
Полнота по бурению: YOLOE 0.65, дообученная 0.05. Источника буровых, снятых с
земли, не существует: в Kaggle их нет совсем (A1), в APOCE они слиты с копрами
и сняты сверху (A2). Наши 45 рамок `drilling_rig` и 15 `pile_driver` —
единственные настоящие примеры в нужном домене.

**Почему это не утечка.** Разрез идёт по площадкам, как требует D-004. Обучающие
и оценочные площадки не пересекаются — тот же принцип, по которому мы забраковали
разрез Захара (A2, п. 1).

**Чем платим.**
- Оценочная выборка ужимается до 2 площадок, метрики станут шумнее.
- p05 входит в демо-график `schedule_demo.csv`: часть цепочки проверяется на
  площадке, которую модель видела. В отчёте и на защите это оговаривается прямо.

**Что сделает решение неверным.** Если прирост на p03/p08 окажется в пределах
шума, значит 151 рамки мало, и правильнее вернуться к D-006, а буровые искать во
внешних открытых источниках (до 5 ссылок разрешено, Q&A 07:56).

## D-015. Правила приводятся к уровню наблюдаемых этапов D-011 — ПРИНЯТО 2026-09-20

**Решение.** `configs/rules.json` перестраивается с уровня кодов работ на уровень
**наблюдаемых этапов D-011**. Правила `12.3.4` (фундаментная плита) и `12.3.9`
(монолит ниже отметки 0) сливаются в одно правило «Фундамент и подземная часть».
Сопоставление «код работы → наблюдаемый этап» остаётся отдельной таблицей, как
и было решено в D-011: справочник и парсер не трогаются.

**Почему.** E5 измерил, что одно наблюдение подтверждает в среднем **2.1 этапа**,
и выделил структурно неразличимую тройку: плита, монолит ниже нуля и каркас выше
нуля обслуживаются одной и той же техникой (башенный кран + автобетоносмеситель).
Но два члена этой тройки **и так объединены** в D-011 — просто это не доехало до
кода. Приведение в соответствие убирает одну ложную неоднозначность **бесплатно,
без единого признака сцены**: различие, которого нет в правилах, не порождает
ложных подтверждений.

**Что остаётся после этого.** Тройка сжимается в пару: **«подземная часть»
против «каркас выше отметки 0»**. Это и есть настоящая граница, и её надо решать
признаком сцены, а не правилами. Ашрапов и соавторы (arXiv 2209.15084) обучались
на близкой онтологии и получили precision 25–45 на подземных стадиях против
**85 на каркасе**: граница качества проходит ровно по отметке 0. Значит
**различать три равноценных класса не нужно и не получится — достаточно бинарного
«на отметке 0 и ниже» против «выше отметки 0»**, потому что вредит именно
преждевременное подтверждение каркаса.

**Вторая пара — `10.3` снос против `12.3.1` котлован** (экскаватор + самосвал) —
зрением не разделяется: прямых работ нет, единственное фактическое наблюдение
отрицательное. Закрывается бесплатным порядковым ограничением по графику: снос
не может идти после начала котлована на той же захватке. Это снимает ровно те
случаи E5, где «снос» всплыл на площадках со сваями.

**Как проверяем, что стало лучше.** Повторный прогон `tools/eda_stage_ambiguity.py`:
целевое значение — **2.1 → 1.3–1.5 этапа на наблюдение**. Метрика считается на
ручной разметке, поэтому не зависит от качества детектора.

**Что сделает решение неверным:** если на вход подадут график, где плита и
монолит ниже нуля имеют существенно разные плановые даты и заказчик потребует
различать их по отдельности. Тогда различение придётся возвращать — но уже
признаком сцены, а не правилом по технике.

## D-016. Процент готовности по фото не обещаем — ПРИНЯТО 2026-09-20

**Решение.** В интерфейсе, документации и на защите **не заявляется** числовая
оценка процента готовности объекта по снимкам. Вместо неё — наблюдаемое
соответствие состава техники этапу, измеренный сдвиг в днях и доказательства.

**Почему.** Разбор 23 продуктов рынка (`research/part_Q_products.md`) даёт чёткую
линию: процент готовности считается алгоритмически **только там, где есть BIM с
геометрией каждого элемента** — Buildots, Doxel, Avvir. Везде без BIM — включая
российские Exon и Тангл — процент либо не считается вовсе, либо берётся из
чек-листов и ручного ввода, а CV выступает подтверждающим доказательством.
У нас BIM нет и не будет (D-010, Q&A 38:25). Оценок процента готовности по
одиночному кадру в литературе не измерено вообще, а отраслевая практика
оценивает завышение отчётного процента людьми в 8–12 процентных пунктов.

**Что при этом можно.** Заказчик спрашивал про оценку процента готовности
(Q&A 36:54) — отказ надо не прятать, а объяснять: это не наша слабость, а
устройство рынка без BIM. Порядковый признак «отметка работ относительно нуля»
и этажность (D-015) — это честная замена, дающая направление и порядок, но не
число с процентами.

**Что сделает решение неверным:** появление на входе BIM или хотя бы поэтажного
плана с объёмами. Тогда процент становится вычислимым, и запрет снимается.

## D-017. Простой техники: доля с интервалом вместо вердикта по кадру — ПРИНЯТО 2026-09-21

**Решение.** Система **не утверждает**, что конкретная машина простаивает на
конкретном кадре. Выдаются две величины:
- **вовлечённость** `engaged` / `not_engaged` / `unknown` на машину — по
  однокадровым признакам, с протоколом `LABELING_SPEC.md` §7c;
- **доля наблюдений без признаков вовлечённости** по классу техники за период,
  метод work sampling, с интервалом Уилсона и порогом 10 определённых
  наблюдений. Меньше порога — доля не оценивается, и отчёт это пишет.

**Почему.** Требование 11:58 «определять факт работы и факт простоя» в
формулировке «по одному кадру про конкретную машину» не наблюдаемо: работа и
простой различаются производной по времени. Литература 2007–2026 не знает ни
одного метода без разности кадров (part_N). Заказчик на 21:53 сам предложил
судить по зоне нахождения техники, то есть по вовлечённости.

**Что измерено.** Согласие двух разметчиков (E15): 70%, каппа 0.47; по
экскаваторам 85%, по буровым 69%, по кранам 55%. Автоматический расчёт на
идеальной разметке (E17): 98% `unknown` — однокадровые признаки в домене
фотоотчётов не работают.

**Что обещаем заказчику.** Механизм работает и показывает долю там, где хватает
наблюдений; на выданных фотоотчётах наблюдений не хватает, и отчёт об этом
говорит. На рядах с камер (кадр раз в 20–30 мин) добавляется смещение рамки
между кадрами — единственный признак, работающий в литературе.

**Что сделает решение неверным.** Если на архиве с камер смещение рамки за
20–30 минут окажется неинформативным (техника успевает вернуться в то же
положение), придётся честно сузить функцию до «вне рабочей зоны» и сказать об
этом прямо.
